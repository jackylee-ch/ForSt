# 2026-05-30 — Why v3.8 "looked" 3×+ better: a measurement artifact, not a real regression

## Question (user directive)
"Check why we have better performance for v3.8." v3.8 reported forst-rs winning
18/23 Nexmark queries vs rocksdb (q4 5.4×, q7 8.4×, q9 9.6×, q15 15×, q20 8×,
q23 20×), yet this session's reliable full sweep measured forst-rs at **0.33×**
(3× SLOWER). What changed?

## Answer: v3.8 was NEVER actually better — its forst-rs numbers are a nexmark peak-TPS extrapolation
v3.8's "wall-clock seconds" (report §L4.1) are **not** real completion wall-clock.
Per its own Methodology (§"Bench harness", line 264-267) the forst-rs column came
from `nexmark-flink/bin/run_query.sh oa <q>` with the **10-min Nexmark monitor**.
That monitor reports `Time = EventsNum / sampled-peak-TPS` — an EXTRAPOLATION from
a sampled peak-throughput window, NOT the time to actually process 100 M records.

This session proved (q9-correctness run, JM operator record counts) that on
state-heavy queries forst-rs **bursts at startup** (source fills buffers/memtable
fast before join/window state grows) then **collapses** to ~16–33 K rec/s as state
grows. The nexmark monitor samples the early burst and extrapolates a fictitious
completion Time. Example: v3.8 q9 = 54.78 s ⇒ implied 1.83 M rec/s SUSTAINED; the
REAL sustained rate is ~16 K/s (q9 never finishes 100 M inside 1500 s). The 54.78 s
is a ~100× fiction.

## The proof: cross-validate against rocksdb (steady throughput)
The rocksdb baseline in v3.8 was *carried verbatim from v3.2* (report §"Why rocksdb
NOT re-bench") — same nexmark metric. But rocksdb has STEADY throughput (no
burst-collapse), so its nexmark Time ≈ true completion. Comparing the v3.2-carried
rocksdb Time against THIS session's real JM-wall-clock sweep:

| Q | rocksdb v3.2 nexmark-Time | rocksdb 2026-05-30 real JM wall-clock | match? |
|---|---:|---:|---|
| q0  | 19.75 | 23.5  | ✓ ~match |
| q4  | 251.78| 246.6 | ✓ match |
| q7  | 459.84| 326.4 | ✓ ~match |
| q8  | 35.16 | 30.4  | ✓ match |
| q9  | 525.15| 554.5 | ✓ match |
| q15 | 279.01| 265.6 | ✓ match |
| q20 | 439.51| 391.4 | ✓ ~match |

rocksdb's nexmark Time tracks real wall-clock within ~10–30%. Now forst-rs:

| Q | forst-rs v3.8 nexmark-Time | forst-rs 2026-05-30 real JM wall-clock | inflation |
|---|---:|---:|---|
| q4  | 46.88 | NA (>1500, ~33K/s) | ≥32× |
| q7  | 54.62 | NA (>1500, ~30K/s) | ≥27× |
| q8  | 23.35 | 148.8 (FINISHED)   | 6.4× |
| q9  | 54.78 | NA (>1500, ~16K/s) | ≥27× |
| q15 | 18.34 | NA (>1500)         | ≥80× |
| q20 | 55.14 | NA (>1500)         | ≥27× |

**The asymmetry is the smoking gun:** the SAME nexmark metric is accurate for
rocksdb (steady) and inflates forst-rs 6–100× (burst-collapse). v3.8 therefore
compared *inflated* forst-rs Time against *honest* rocksdb Time → the "18/23 wins"
and "5–20× / 113×" headlines are measurement artifacts. Even q8 — which COMPLETES
in both — shows the inflation cleanly: 23.35 (nexmark) vs 148.8 (real) = 6.4×.

## Consequences
1. **There is no real v3.8→HEAD perf regression to "recover."** forst-rs was not
   genuinely faster than rocksdb on state-heavy queries in v3.8; it only looked so
   under the peak-TPS metric. The honest q0–q22 picture has consistently been
   ~0.3–0.5× on the state-heavy half whenever measured by true completion.
2. **The 3× goal was likely never met in any version** by honest wall-clock — every
   prior "win" (v3.2, v3.8, the retracted q4=207s/q9=54× this session) traces to the
   same nexmark sampled-peak extrapolation.
3. **The real path to 3× is genuine per-record CPU optimization**, not restoration.
   The wall is ~20 K rec/s engine CPU on heavy join/window state (dual-index memtable
   write + double-pass read resolution), storage-independent (q7-LOCAL == q7-S3 rate).
   See 2026-05-30-prefix-scan-value-carrying-cpu-lever.md and
   [[project_full_sweep_2026-05-29]].

## What v3.8 DID do for batch execution (the real, kept improvements)
v3.8's genuine architectural work — still in HEAD — was reducing per-op FFM
crossings via BATCHING: the batched off-heap engine timer (`a5fd9f70dd6`:
`frsBatchPut`/`frsVectorizedBatchDelete`/`frsBatchPrefixScan`) and the batched FFM
state primitives (`frsVectorizedBatchGet`/`batchPut`/`batchPrefixScan`). These are
real and correct; they cut the per-event boundary cost. They do NOT, however, make
the *per-record engine work* (memtable insert + tier-walk value resolution) fast
enough to beat rocksdb-local on true completion — which is why even with them the
honest rate is ~20 K/s. One post-v3.8 narrowing worth a real-wall-clock A/B:
`VectorizedExecutor.requiresOrderedDispatch` (added after v3.8) can route RMW
batches (q4/q7 GET+PUT same-key) into per-row sync dispatch — a partial defeat of
the batch path — though it is gated behind delete/append-merge presence.

## Method lesson (reinforced)
Trust ONLY real JM `/jobs/<id>` completion wall-clock (Source write-records = 100 M
AND state=FINISHED). NEVER the nexmark Summary Time/throughput — it is sampled-peak
extrapolation that is accurate for steady engines and wildly optimistic for
burst-then-collapse ones. This single methodology error produced years of
forst-rs "wins" that real completion does not support.
