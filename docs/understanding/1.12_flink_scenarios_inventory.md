## 2. 逐场景详细分析

### 场景 1: ValueState get/put (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 异步版实现

- **关键类**: `ForStValueState<K, N, V>` (继承 `AbstractValueState<K, N, V>`)
- **源码路径**: `flink-statebackend-forst/.../ForStValueState.java`
- **API**: State v2 (`org.apache.flink.api.common.state.v2.ValueState`)

**Get 调用链**:
```
user.asyncValue()
  -> AbstractValueState.handleRequest(VALUE_GET, null)
    -> AEC 收集批次 -> ForStStateExecutor.executeBatchRequests()
      -> ForStStateRequestClassifier: innerTable.buildDBGetRequest()
        -> new ForStDBSingleGetRequest(contextKey, this, future)
          -> ForStGeneralMultiGetOperation.process()
            -> request.buildSerializedKey()  // SerializedCompositeKeyBuilder
            -> db.multiGetAsList(readOptions, cfHandles, keys)  // JNI
            -> table.deserializeValue(bytes) -> future.complete(value)
```

**Put 调用链**:
```
user.asyncUpdate(value)
  -> AbstractValueState.handleRequest(VALUE_UPDATE, value)
    -> ForStStateRequestClassifier: innerTable.buildDBPutRequest()
      -> ForStDBPutRequest.of(contextKey, value, this, future)
        -> ForStWriteBatchOperation.process()
          -> writeBatch.put(cfHandle, serializedKey, serializedValue)  // JNI
          -> writeBatch.flush()  // db.write(WriteOptions, WriteBatch)
```

**Clear 调用链**:
```
user.asyncClear()
  -> handleRequest(CLEAR, null)
    -> ForStDBPutRequest.of(contextKey, null, this, future)  // value=null
      -> writeBatch.remove(cfHandle, serializedKey)  // JNI delete
```

**JNI 边界调用**:
- 读: `RocksDB.multiGetAsList(ReadOptions, List<ColumnFamilyHandle>, List<byte[]>)`
- 写: `WriteBatch.put(ColumnFamilyHandle, byte[], byte[])` + `RocksDB.write(WriteOptions, WriteBatch)`
- 删: `WriteBatch.delete(ColumnFamilyHandle, byte[])`

#### 同步版实现

- **关键类**: `ForStSyncValueState<K, N, V>` (继承 `AbstractForStSyncState`)
- **源码路径**: `flink-statebackend-forst/.../sync/ForStSyncValueState.java`
- **API**: State v1 (`org.apache.flink.api.common.state.ValueState`)

**执行模型差异**:
- 同步版通过 `setCurrentKey(K)` 设置全局 key，然后直接调用 `db.get()` / `db.put()`
- 无批量处理，每次操作独立完成
- 使用非线程安全的共享 `sharedRocksKeyBuilder` 序列化 key

**JNI 边界调用**:
- 读: `RocksDB.get(ColumnFamilyHandle, ReadOptions, byte[])`（单条）
- 写: 通过 `ForStDBWriteBatchWrapper` 累积，超过阈值自动 flush

**差距**: 无。两版均完整实现。

### 场景 2: ListState add/get/clear (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 异步版实现

- **关键类**: `ForStListState<K, N, V>` (继承 `AbstractListState`)
- **源码路径**: `flink-statebackend-forst/.../ForStListState.java`
- **辅助类**: `ListDelimitedSerializer` (列表序列化)、`ForStDBListGetRequest` (批量 Get)

**操作映射**:

| 操作 | StateRequestType | DB 请求类型 | RocksDB 操作 |
|------|-----------------|------------|-------------|
| asyncGet() | LIST_GET | ForStDBListGetRequest | multiGetAsList → ListDelimitedSerializer.deserializeList() |
| asyncAdd(value) | LIST_ADD | ForStDBPutRequest (merge) | writeBatch.merge() |
| asyncAddAll(values) | LIST_ADD_ALL | ForStDBPutRequest (merge) | writeBatch.merge() |
| asyncUpdate(values) | LIST_UPDATE | ForStDBPutRequest (覆盖) | writeBatch.put() |
| asyncClear() | CLEAR | ForStDBPutRequest (null) | writeBatch.remove() |

**关键技术**: ListState 使用 RocksDB 的 **StringAppendOperator (Merge Operator)** 实现高效的列表追加。`writeBatch.merge()` 将新元素追加到现有值末尾，避免 read-modify-write 模式。

**JNI 边界调用**:
- 读: `RocksDB.multiGetAsList()` + Java 侧 `ListDelimitedSerializer.deserializeList()`
- 写: `WriteBatch.merge(ColumnFamilyHandle, byte[], byte[])` — **Merge Operator 依赖**
- 覆盖写: `WriteBatch.put()`
- 删: `WriteBatch.delete()`

#### 同步版实现

- **关键类**: `ForStSyncListState<K, N, V>`
- **源码路径**: `flink-statebackend-forst/.../sync/ForStSyncListState.java`
- 同步版同样使用 merge 操作实现 add

**差距**: 无功能差距。但 **Merge Operator 是 RocksDB 特有机制**，ForSt-RS 必须实现兼容的 merge operator（StringAppendOperator 语义）才能支持 ListState。

### 场景 3: MapState put/get/keys/values/entries/iterator (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 异步版实现

- **关键类**: `ForStMapState<K, N, UK, UV>` (继承 `AbstractMapState`)
- **源码路径**: `flink-statebackend-forst/.../ForStMapState.java`
- **辅助类**: `ForStDBMapCheckRequest`、`ForStDBBunchPutRequest`、`ForStDBMapEntryIterRequest`、`ForStDBMapKeyIterRequest`、`ForStDBMapValueIterRequest`、`ForStMapIterator`

MapState 是最复杂的状态类型：每个 `(key, namespace, userKey)` 三元组对应一个 RocksDB 条目。

**操作映射**:

| 操作 | StateRequestType | DB 请求类型 | RocksDB 操作 |
|------|-----------------|------------|-------------|
| asyncGet(UK) | MAP_GET | ForStDBSingleGetRequest | multiGetAsList (含 userKey 的复合 key) |
| asyncPut(UK, UV) | MAP_PUT | ForStDBPutRequest | writeBatch.put() |
| asyncPutAll(Map) | MAP_PUT_ALL | ForStDBBunchPutRequest | writeBatch.put() (每个 entry) |
| asyncRemove(UK) | MAP_REMOVE | ForStDBPutRequest (null) | writeBatch.delete() |
| asyncContains(UK) | MAP_CONTAINS | ForStDBMapCheckRequest | db.get() (单独执行) |
| asyncIsEmpty() | MAP_IS_EMPTY | ForStDBMapCheckRequest | db.newIterator() + seek (前缀扫描) |
| asyncIterator() | MAP_ITER | ForStDBMapEntryIterRequest | db.newIterator() + seek + scan |
| asyncKeys() | MAP_ITER_KEY | ForStDBMapKeyIterRequest | db.newIterator() + seek + scan |
| asyncValues() | MAP_ITER_VALUE | ForStDBMapValueIterRequest | db.newIterator() + seek + scan |
| asyncClear() | CLEAR (Map) | ForStDBBunchPutRequest | 前缀扫描删除所有 userKey |

**Key 编码格式**: `[KeyGroupPrefix(1-2 bytes)][SerializedKey][SerializedNamespace][UserKey]`

**迭代器机制**:
- `ForStIterateOperation.process()` 执行迭代
- 迭代器使用前缀扫描：`iterator.seek(prefix)` 后逐条读取，直到前缀不匹配
- 支持分批加载：通过 `cacheSizeLimit` 限制单批加载量
- 未读完的数据通过 `ITERATOR_LOADING` 请求继续加载

**JNI 边界调用**:
- 读: `RocksDB.multiGetAsList()` (get)、`RocksDB.get()` (contains)
- 写: `WriteBatch.put()` / `WriteBatch.delete()`
- 迭代: `RocksDB.newIterator(ColumnFamilyHandle)` + `RocksIterator.seek(byte[])` + `.isValid()` / `.key()` / `.value()` / `.next()`

#### 同步版实现

- **关键类**: `ForStSyncMapState<K, N, UK, UV>`
- **源码路径**: `flink-statebackend-forst/.../sync/ForStSyncMapState.java`
- 同步版使用 `ForStIteratorWrapper` 封装 RocksIterator

**差距**: 无功能差距。MapState 是 ForSt-RS 实现复杂度最高的状态类型，因为涉及 iterator 管理和前缀扫描。

### 场景 4: AggregatingState add/get (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 异步版实现

- **关键类**: `ForStAggregatingState<K, N, IN, ACC, OUT>` (继承 `AbstractAggregatingState`)
- **源码路径**: `flink-statebackend-forst/.../ForStAggregatingState.java`

**操作映射**:

| 操作 | StateRequestType | 底层 DB 操作 | 说明 |
|------|-----------------|-------------|------|
| asyncGet() | AGGREGATING_GET | multiGetAsList → ACC → aggregateFunction.getResult(ACC) → OUT | DB 层只存 ACC |
| asyncAdd(IN) | AGGREGATING_ADD | **AEC 层 read-modify-write**: get ACC → aggregateFunction.add(IN, ACC) → put 新 ACC | 非原子操作 |
| asyncClear() | CLEAR | writeBatch.delete() | 标准删除 |

**关键机制**: AggregatingState 的 `add` 操作在 **AEC (AsyncExecutionController) 层面**执行 read-modify-write。底层 ForSt 只看到独立的 get 和 put 操作。AEC 负责保证同一 key 的操作有序执行。

**JNI 边界调用**:
- 读: `RocksDB.multiGetAsList()` — 获取 ACC 字节
- 写: `WriteBatch.put()` — 写入新 ACC 字节

#### 同步版实现

- **关键类**: `ForStSyncAggregatingState<K, N, IN, ACC, OUT>` (继承 `AbstractForStSyncAppendingState`)
- **源码路径**: `flink-statebackend-forst/.../sync/ForStSyncAggregatingState.java`
- 同步版在 `add()` 方法内直接执行 get → aggregate → put

**差距**: 无。两版功能等价，区别在于 read-modify-write 的执行位置（AEC 层 vs 方法内部）。

---

### 场景 5: ReducingState add/get (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 异步版实现

- **关键类**: `ForStReducingState<K, N, V>` (继承 `AbstractReducingState`)
- **源码路径**: `flink-statebackend-forst/.../ForStReducingState.java`

**操作映射**:

| 操作 | StateRequestType | 底层 DB 操作 | 说明 |
|------|-----------------|-------------|------|
| asyncGet() | REDUCING_GET | multiGetAsList → V | 直接读取 |
| asyncAdd(V) | REDUCING_ADD | **AEC 层 read-modify-write**: get 旧值 → reduceFunction.reduce(旧值, 新值) → put 结果 | 非原子操作 |
| asyncClear() | CLEAR | writeBatch.delete() | 标准删除 |

**关键机制**: 与 AggregatingState 相同，`add` 操作在 AEC 层执行 read-modify-write。底层 ForSt 只看到 get + put。

**JNI 边界调用**: 与 ValueState 相同 — `multiGetAsList()` + `WriteBatch.put()`

#### 同步版实现

- **关键类**: `ForStSyncReducingState<K, N, V>` (继承 `AbstractForStSyncAppendingState`)
- **源码路径**: `flink-statebackend-forst/.../sync/ForStSyncReducingState.java`

**差距**: 无。与 AggregatingState 模式一致。

### 场景 6: Incremental Checkpoint (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

- **关键类**: `ForStIncrementalSnapshotStrategy` (继承 `ForStNativeFullSnapshotStrategy`)
- **源码路径**: `flink-statebackend-forst/.../snapshot/ForStIncrementalSnapshotStrategy.java`
- **辅助类**: `ForStSnapshotStrategyBase`、`ForStStateDataTransfer`、`DataTransferStrategy`

#### 完整流程

**同步阶段** (Task 线程):
1. `snapshotMetaData()` — 构建 PreviousSnapshot (已上传 SST 文件映射)
2. `db.disableFileDeletions()` — 阻止 compaction 删除文件
3. `db.getLiveFiles(true)` — flush memtable + 获取活跃文件列表
4. 构建 `ForStNativeSnapshotResources`

**异步阶段** (异步线程池):
1. `classifyFiles()` — SST 差分追踪:
   - 已上传 SST → `PlaceholderStreamStateHandle` (零拷贝复用)
   - 新 SST → 加入 `toTransferSstFiles` 列表
   - MANIFEST → 单独传输
   - CURRENT → 异步重写
2. 元数据序列化 (`KeyedBackendSerializationProxy`)
3. `ForStStateDataTransfer.transferFilesToCheckpointFs()` — 多线程上传新文件
4. 记录 `uploadedSstFiles[checkpointId]`
5. 返回 `IncrementalRemoteKeyedStateHandle`

**完成通知**:
- `notifyCheckpointComplete()` — 更新 `lastCompletedCheckpointId`，清理过期记录
- `notifyCheckpointAborted()` — 清理 aborted 记录

**JNI 边界调用**:
- `RocksDB.disableFileDeletions()` / `enableFileDeletions()`
- `RocksDB.getLiveFiles(boolean flushMemtable)`
- 文件 I/O 不通过 JNI，而是 Java 文件系统 API

**SharingFilesStrategy 处理**:
- `FORWARD_BACKWARD` — 增量 checkpoint，复用 PreviousSnapshot
- `NO_SHARING` — Savepoint，所有文件上传为 EXCLUSIVE scope
- `FORWARD` — Full checkpoint (对增量策略有限制)

**差距**: 无功能差距。但 SST 差分追踪逻辑复杂，涉及 PreviousSnapshot 剪枝逻辑 (`pruneFirstCheckpointSstFiles()`) 处理 TM-JM 通知延迟问题。ForSt-RS 需完整实现此逻辑。

### 场景 7: Full Checkpoint (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

- **关键类**: `ForStNativeFullSnapshotStrategy`
- **源码路径**: `flink-statebackend-forst/.../snapshot/ForStNativeFullSnapshotStrategy.java`

#### 与增量快照的差异

| 维度 | 增量快照 | 全量快照 |
|------|---------|---------|
| SST 差分 | 有 (PreviousSnapshot) | 无 (EMPTY_PREVIOUS_SNAPSHOT) |
| 文件 scope | SHARED (可共享) | EXCLUSIVE (独占) |
| uploadedSstFiles | 维护历史 | 不维护 |
| notifyCheckpointComplete | 更新历史 | 空操作 |
| 结果 handle 的 sstFiles | SST 引用列表 | 空列表 |
| 结果 handle 的 miscFiles | MANIFEST + CURRENT | 所有文件 |

**流程**: 同步阶段与增量相同。异步阶段不做差分，所有活跃文件均上传。最终同样返回 `IncrementalRemoteKeyedStateHandle`，但 sstFiles 为空，所有文件放在 miscFiles (privateFiles)。

**JNI 边界调用**: 与增量快照相同。

**差距**: 无。全量快照是增量快照的简化版。

### 场景 8: Restore from checkpoint (P0)

**支持度**: 异步版 **完整** / 同步版 **完整**

- **关键类**: `ForStIncrementalRestoreOperation`、`ForStNoneRestoreOperation`、`ForStHeapTimersFullRestoreOperation`
- **源码路径**: `flink-statebackend-forst/.../restore/`
- **辅助类**: `ForStHandle` (DB 实例管理)、`ForStRestoreResult` (恢复结果)

#### 恢复策略选择

| 场景 | 恢复操作类 | 描述 |
|------|-----------|------|
| 无 State Handle | `ForStNoneRestoreOperation` | 创建空 ForSt DB |
| 增量 Handle | `ForStIncrementalRestoreOperation` | 下载 SST + 打开 DB |
| 全量/Savepoint Handle | `ForStHeapTimersFullRestoreOperation` | 全量反序列化 + 写入 DB |

#### ForStIncrementalRestoreOperation 详细流程

1. **选择最佳 Handle**: `findTheBestStateHandleForInitial()` — 按 key group 重叠度评分
2. **并行下载**: `ForStStateDataTransfer` (默认 4 线程) 下载所有文件到本地
3. **打开 DB**: 解析 MANIFEST → `ForStHandle.openDB()` → 注册 ColumnFamilyHandle
4. **Key Group 检查**: 范围匹配则恢复增量历史 (backendUID + uploadedSstFiles)；不匹配则执行 `clipDBWithKeyGroupRange()`

**恢复结果** (`ForStRestoreResult`):
- `db` — RocksDB 实例
- `defaultColumnFamilyHandle` — 默认列族
- `lastCompletedCheckpointId` — 最后完成的 CP ID
- `backendUID` — 后端唯一标识
- `restoredSstFiles` — 已恢复的 SST 文件映射

**JNI 边界调用**:
- `RocksDB.open(DBOptions, path, List<ColumnFamilyDescriptor>)`
- `RocksDB.deleteFilesInRanges()` (rescale 时)
- `RocksDB.deleteRange()` (rescale 时)

**差距**: 无功能差距。但恢复路径涉及多种场景组合 (单/多 handle、rescale/非 rescale)，复杂度较高。

### 场景 9: Rescaling (parallelism change) (P1)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 实现位置

Rescaling 在恢复阶段 (`ForStIncrementalRestoreOperation`) 中处理，而非 checkpoint 阶段。

#### Scale-out (并行度增加) — clipDB

当恢复的 State Handle 的 key group 范围大于当前 Task 的范围时：

```
clipDBWithKeyGroupRange():
  1. 计算需要删除的 key group 范围
  2. db.deleteFilesInRanges()  // 快速删除 SST 文件 (JNI)
  3. db.deleteRange()          // 放置范围删除墓碑 (JNI)
```

- **关键类**: `ForStIncrementalCheckpointUtils`
- **源码路径**: `flink-statebackend-forst/.../ForStIncrementalCheckpointUtils.java`

#### Scale-in (并行度减少) — 多 Handle 合并

当需要合并多个 State Handle 时：

```
restoreFromMultipleStateHandles():
  if (useIngestDbRestoreMode):
    选最佳 handle 作 base DB → IngestDB 导入其他 handle
  else:
    选最佳 handle 作 base DB → 逐条遍历其他 handle 写入
```

**JNI 边界调用**:
- `RocksDB.deleteFilesInRanges(ColumnFamilyHandle, byte[][])`
- `RocksDB.deleteRange(ColumnFamilyHandle, byte[], byte[])`
- `RocksDB.ingestExternalFile()` (IngestDB 模式)

**差距**: 功能完整。IngestDB 模式要求 SST key range 不重叠，否则回退到逐条导入，性能差异较大。

### 场景 10: Timer service (event/processing time) (P1)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 实现

Timer Service 通过 `PriorityQueueSetFactory` 接口创建优先级队列。两版均实现此接口。

**同步版实现**:
- **关键类**: `ForStDBCachingPriorityQueueSet` + `ForStDBPriorityQueueSetFactory`
- **源码路径**: `flink-statebackend-forst/.../sync/ForStDBCachingPriorityQueueSet.java`、`ForStDBPriorityQueueSetFactory.java`
- **配置**: `ForStPriorityQueueConfig` 控制优先级队列的存储位置
- **辅助类**: `TreeOrderedSetCache` 提供内存缓存层

**机制**: 使用 RocksDB 存储 + Java `TreeSet` 内存缓存的混合策略。小数据量时全内存操作，溢出后写入 RocksDB。

**异步版实现**:
- `ForStKeyedStateBackend` 实现 `PriorityQueueSetFactory`
- Timer 数据可存储在 RocksDB 或 Heap 中（取决于配置）

**JNI 边界调用**:
- `RocksDB.get()` / `RocksDB.put()` / `RocksDB.delete()` — 优先级队列元素操作
- `RocksDB.newIterator()` — 扫描队列

**差距**: 无功能差距。`ForStDBCachingPriorityQueueSet` 的混合缓存策略在 ForSt-RS 中需要等价实现。

---

### 场景 11: Async state access (P1)

**支持度**: 异步版 **完整** / 同步版 **不适用**

#### 异步版独有架构

这是异步版的核心能力，同步版从设计上就不支持。

**架构组件**:

| 组件 | 类 | 职责 |
|------|-----|------|
| 异步执行控制器 | `AsyncExecutionController (AEC)` | 收集请求、排队、触发批量执行 |
| 状态执行器 | `ForStStateExecutor` | 三线程池 (coordinator + read + write)，批量执行 DB 操作 |
| 请求分类器 | `ForStStateRequestClassifier` | 将 StateRequest 分类为 Get/Put/Iter 三组 |
| 批量读 | `ForStGeneralMultiGetOperation` | 按 readIoParallelism 分片并行 multiGet |
| 批量写 | `ForStWriteBatchOperation` | WriteBatch 一次性提交 |
| 迭代 | `ForStIterateOperation` | 迭代器操作 |
| 上下文键 | `ContextKey<K, N>` | 封装 RecordContext + namespace + userKey，含序列化缓存 |

**线程模型**:
```
+---------------------+
|  Coordinator Thread  |  -- 1 个线程（或 inline），调度
+---------------------+
         |
    +----+----+
    |         |
+-------+  +-------+
| Read  |  | Write |  -- 可配置并行度
| Pool  |  | Pool  |
+-------+  +-------+
```

**背压机制**: `fullyLoaded()` 返回 `ongoing.get() >= readThreadCount` 时 AEC 暂停提交新批次。

**关键差异** (vs 同步版):
- 异步版无全局 `currentKey`，key 通过 `RecordContext<K>` 传递
- 序列化器使用 ThreadLocal（多线程安全）
- 所有 State API 返回 `StateFuture<T>`

**差距**: 同步版不支持异步访问。这是 Flink 2.x State v2 API 的核心特性，ForSt-RS 必须完整实现。

---

### 场景 12: TTL state (P1)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 实现

**异步版**:
- TTL 通过 `TtlStateFactory` (v2 版本，位于 `state.v2.ttl` 包) 包装原始 State
- 在 `AbstractKeyedStateBackend` 的 `getOrCreateKeyedState()` 中，如果 `StateDescriptor` 配置了 TTL，则通过 TtlStateFactory 包装

**同步版**:
- TTL 通过 `TtlStateFactory` (v1 版本) 包装
- 在 `AbstractKeyedStateBackend.getOrCreateKeyedState()` 中处理

**Compaction Filter 机制**:
- **关键类**: `ForStDBTtlCompactFiltersManager`
- **源码路径**: `flink-statebackend-forst/.../ForStDBTtlCompactFiltersManager.java`
- TTL 过期的数据通过 RocksDB **Compaction Filter** 在后台清理
- 每个 ColumnFamily 注册对应的 TTL compact filter

**JNI 依赖**:
- Compaction Filter 是 RocksDB 原生功能，通过 JNI 注册到 `ColumnFamilyOptions`
- ForSt-RS 需要在 Rust 存储层实现等价的 compaction filter 机制

**差距**: 功能完整。但 **Compaction Filter 是 RocksDB 特有机制**，ForSt-RS 需要：
1. 在 Rust compaction 流程中实现 TTL 过期判断
2. 通过 JNI 暴露 filter 注册接口
3. 保持 TTL 值的序列化格式兼容（时间戳前缀）

---

### 场景 13: State migration (schema evolution) (P1)

**支持度**: 异步版 **部分支持** / 同步版 **完整支持**

#### 同步版

- State migration 在 `AbstractKeyedStateBackend.getOrCreateKeyedState()` 中处理
- 当检测到注册的 `TypeSerializer` 与恢复的 `TypeSerializerSnapshot` 不兼容时，执行数据迁移
- 遍历所有 key，使用旧序列化器反序列化 → 使用新序列化器重新序列化 → 写入

#### 异步版

- **关键证据**: 文档 1.4 (Section 6, Open Question 5) 明确指出：
  > "当前异步版 ForSt 的状态迁移（序列化器变更）尚未完全实现（见源码中的 `TODO: 2024/6/6 - Implement state migration`）"
- `ForStKeyedStateBackend.getOrCreateKeyedState()` 中存在 TODO 标记

**差距**: **异步版存在明确的实现缺失**。源码中有 TODO 标记表明 state migration 尚未在异步路径中完整实现。这意味着：
1. 当用户变更状态的序列化格式时，异步版可能无法自动迁移
2. 需要回退到同步版或手动处理

**ForSt-RS 影响**: 如果 ForSt-RS 基于异步版实现，需要补全 state migration 逻辑。

---

### 场景 14: Queryable state (P2)

**支持度**: 异步版 **已废弃** / 同步版 **已废弃**

#### 状态

Queryable State 在 Flink 2.x 中已被标记为 **@Deprecated** 并最终移除。该功能允许外部客户端直接查询 Task 的状态，但由于架构复杂性和维护成本，社区决定废弃。

**证据**:
- Flink 2.x 中 `QueryableStateClient` 和相关类已被移除或废弃
- ForSt 的异步版和同步版均未实现 queryable state 接口

**差距**: 无需实现。ForSt-RS 不需要支持此功能。

---

### 场景 15: Savepoint compatibility (P2)

**支持度**: 异步版 **完整** / 同步版 **完整**

#### 实现

Savepoint 通过 `ForStNativeFullSnapshotStrategy` 的特殊模式处理。

**与普通 Checkpoint 的差异**:

| 维度 | 增量 Checkpoint | Savepoint |
|------|----------------|-----------|
| SharingFilesStrategy | FORWARD_BACKWARD | NO_SHARING |
| PreviousSnapshot | 基于 uploadedSstFiles | EMPTY (所有文件都上传) |
| 文件 scope | SHARED | EXCLUSIVE |
| SST 复用 | 有 (PlaceholderStreamStateHandle) | 无 (所有文件完整上传) |
| 结果格式 | IncrementalRemoteKeyedStateHandle | 同 (但所有文件 EXCLUSIVE) |

**Savepoint 恢复**: 通过 `ForStHeapTimersFullRestoreOperation` 处理，执行全量反序列化 + 写入 DB。

**KeyedStateHandle 层次中的 Savepoint 标记**:
- `SavepointKeyedStateHandle` — 标记接口
- `KeyGroupsSavepointStateHandle` — 继承 `KeyGroupsStateHandle` + `SavepointKeyedStateHandle`

**差距**: 无功能差距。Savepoint 本质是全量快照的特殊模式。

## 4. ForSt-RS 重构影响分析

### 4.1 每场景替换边界

| # | 场景 | ForSt-RS 替换范围 | 是否可保留 Java 层 |
|---|------|------------------|-------------------|
| 1 | ValueState | JNI 层替换 (multiGet/writeBatch) | **是** — ForStValueState 可原样保留 |
| 2 | ListState | JNI 层替换 + **Merge Operator 实现** | **是** — 但需 Rust 实现 StringAppendOperator |
| 3 | MapState | JNI 层替换 (含 Iterator) | **是** — ForStMapState 可原样保留 |
| 4 | AggregatingState | JNI 层替换 | **是** — AEC 层 read-modify-write 在 Java 侧 |
| 5 | ReducingState | JNI 层替换 | **是** — 同上 |
| 6 | Incr. Checkpoint | JNI 层替换 + **SST 文件管理** | **部分** — 快照策略需适配 Rust DB |
| 7 | Full Checkpoint | JNI 层替换 | **部分** — 同上 |
| 8 | Restore | JNI 层替换 + **DB open 兼容** | **部分** — ForStHandle 需适配 |
| 9 | Rescaling | JNI 层替换 + **deleteFilesInRanges** | **部分** — 需 Rust 侧 SST 文件范围删除 |
| 10 | Timer | JNI 层替换 | **是** — 优先级队列可保留 |
| 11 | Async access | 无需替换 (纯 Java 层) | **是** — ForStStateExecutor 可原样保留 |
| 12 | TTL | JNI 层替换 + **Compaction Filter** | **部分** — 需 Rust compaction filter |
| 13 | State migration | 需补全异步版实现 | **需新增** |
| 14 | Queryable state | 无需实现 | N/A |
| 15 | Savepoint | 与 Full Checkpoint 相同 | **部分** |

### 4.2 关键差距汇总

| 差距类型 | 涉及场景 | 严重度 | 说明 |
|----------|---------|--------|------|
| **Merge Operator** | 场景 2 (ListState) | **高** | Rust 存储层必须实现 StringAppendOperator 语义 |
| **Compaction Filter** | 场景 12 (TTL) | **高** | Rust compaction 流程中需实现 TTL 过期判断 |
| **SST 文件管理** | 场景 6, 7, 8, 9 | **高** | disableFileDeletions/getLiveFiles/deleteFilesInRanges 需 Rust 等价实现 |
| **Iterator 前缀扫描** | 场景 3 (MapState) | **中** | Rust DB 需支持前缀扫描语义 |
| **State Migration** | 场景 13 | **中** | 异步版源码有 TODO 标记，需补全 |
| **IngestDB** | 场景 9 (Rescaling) | **低** | 可回退到逐条导入 |

## 5. 场景优先级与实现建议

### Phase 1 — P0 核心 (必须)

**目标**: 覆盖场景 1-8，实现基本功能闭环。
