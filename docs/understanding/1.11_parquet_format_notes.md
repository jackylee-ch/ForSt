## 1. Context

Apache Parquet 是大数据生态中事实上的列式存储标准。ForSt-RS 计划使用基于 Arrow 的自定义 SST 格式来存储 KV 数据，其设计需要解决的核心问题 -- Footer 组织、索引结构、Bloom Filter、数据编码与压缩 -- 与 Parquet 高度重叠。研究 Parquet 的设计要素，可以：

1. **借鉴其经过生产验证的 Footer-at-end 模式**：数据先写、元数据后写，支持 single-pass 写入
2. **参考其多层索引体系**（Column Index / Offset Index / Bloom Filter）的设计权衡
3. **理解列式编码策略**（Dictionary、RLE、Delta）如何最大化压缩比
4. **规避已知陷阱**：如 LZ4 framing 的兼容性问题、Thrift 元数据解析的性能瓶颈

ForSt-RS SST 的目标与 Parquet 不同 -- 它存储的是按 Key 排序的 KV 对（类似 LSM-Tree 的 SSTable），而非 OLAP 分析场景下的宽表。但二者在文件物理布局、索引设计、Bloom Filter 等方面有大量共性。

## 3. 发现

### 3.1 Parquet 文件整体结构

Parquet 文件采用分层的物理结构，核心设计理念是 **"metadata at the end"** -- 数据在前，元数据在后，支持 single-pass 顺序写入。

```
┌─────────────────────────────────────────────────┐
│  Magic Number: "PAR1" (4 bytes)                 │
├─────────────────────────────────────────────────┤
│  Row Group 1                                    │
│  ┌─────────────────────────────────────────┐    │
│  │  Column Chunk 1 (col_a)                 │    │
│  │  ┌──────────────────────────────────┐   │    │
│  │  │  [Dictionary Page] (optional)    │   │    │
│  │  │  [Data Page 1]                   │   │    │
│  │  │  [Data Page 2]                   │   │    │
│  │  │  ...                             │   │    │
│  │  └──────────────────────────────────┘   │    │
│  │  Column Chunk 2 (col_b)                 │    │
│  │  ┌──────────────────────────────────┐   │    │
│  │  │  [Dictionary Page] (optional)    │   │    │
│  │  │  [Data Page 1]                   │   │    │
│  │  │  ...                             │   │    │
│  │  └──────────────────────────────────┘   │    │
│  │  ...Column Chunk N                      │    │
│  └─────────────────────────────────────────┘    │
├─────────────────────────────────────────────────┤
│  Row Group 2                                    │
│  └── ...                                        │
├─────────────────────────────────────────────────┤
│  ...Row Group M                                 │
├─────────────────────────────────────────────────┤
│  (Optional) Bloom Filter Data                   │
│  (Optional) Column Index / Offset Index         │
├─────────────────────────────────────────────────┤
│  File Metadata (Thrift TCompactProtocol)        │
├─────────────────────────────────────────────────┤
│  File Metadata Length (4 bytes, little-endian)   │
├─────────────────────────────────────────────────┤
│  Magic Number: "PAR1" (4 bytes)                 │
└─────────────────────────────────────────────────┘
```

**层次关系**：

| 层次 | 说明 | 典型大小 |
|------|------|----------|
| **File** | 包含 1+ Row Groups | 数百 MB ~ 数 GB |
| **Row Group** | 行的水平分区，包含每列一个 Column Chunk | 推荐 512MB ~ 1GB |
| **Column Chunk** | 单列在一个 Row Group 内的全部数据 | 取决于列数据量 |
| **Page** | 最小 I/O 和编码单元 | 推荐 8KB ~ 1MB |

**关键设计选择**：
- Footer 在文件末尾，Reader 先读末尾 8 字节（4 bytes metadata length + 4 bytes magic），然后定位并读取 Footer
- 支持将列拆分到多个文件，一个 metadata 文件引用多个数据文件
- Row Group 是并行处理的基本单位（MapReduce 粒度）
- Page 是编码和压缩的最小单位，不可再分

### 3.2 Footer 结构 (FileMetaData)

Footer 使用 **Thrift TCompactProtocol** 序列化，核心结构定义如下（简化自 `parquet.thrift`）：

```thrift
struct FileMetaData {
  1: required i32 version;                    // 文件版本 (1 或 2)
  2: required list<SchemaElement> schema;      // 扁平化的 Schema 树
  3: required i64 num_rows;                    // 总行数
  4: required list<RowGroup> row_groups;       // Row Group 列表
  5: optional list<KeyValue> key_value_metadata; // 自定义 KV 元数据
  6: optional string created_by;              // 写入程序标识
  7: optional list<ColumnOrder> column_orders; // 列排序规则
}

struct RowGroup {
  1: required list<ColumnChunk> columns;      // 按 Schema 顺序的列
  2: required i64 total_byte_size;            // 未压缩总大小
  3: required i64 num_rows;                   // 行数
  4: optional list<SortingColumn> sorting_columns; // 排序列信息
  5: optional i64 file_offset;                // Row Group 在文件中的起始偏移
  6: optional i64 total_compressed_size;      // 压缩后总大小
  7: optional i16 ordinal;                    // Row Group 序号
}

struct ColumnChunk {
  1: optional string file_path;               // 列数据文件（跨文件时使用）
  2: required i64 file_offset;                // 列数据在文件中的起始偏移
  3: optional ColumnMetaData meta_data;       // 列元数据（实际为 required）
  4: optional i64 offset_index_offset;        // OffsetIndex 偏移
  5: optional i32 offset_index_length;        // OffsetIndex 长度
  6: optional i64 column_index_offset;        // ColumnIndex 偏移
  7: optional i32 column_index_length;        // ColumnIndex 长度
}

struct ColumnMetaData {
  1:  required Type type;                     // 物理类型
  2:  required list<Encoding> encodings;      // 使用的编码列表
  3:  required list<string> path_in_schema;   // Schema 路径
  4:  required CompressionCodec codec;        // 压缩算法
  5:  required i64 num_values;                // 值总数
  6:  required i64 total_uncompressed_size;   // 未压缩大小
  7:  required i64 total_compressed_size;     // 压缩后大小
  8:  required i64 data_page_offset;          // 第一个 Data Page 偏移
  9:  optional i64 index_page_offset;         // Index Page 偏移
  10: optional i64 dictionary_page_offset;    // Dictionary Page 偏移
  12: optional Statistics statistics;          // 列级统计信息 (min/max/null_count)
  14: optional i64 bloom_filter_offset;       // Bloom Filter 数据偏移
  15: optional i32 bloom_filter_length;       // Bloom Filter 数据长度
}
```

**Page Header 结构**（inline 存储于每个 Page 之前）：

```thrift
struct PageHeader {
  1: required PageType type;                  // DATA_PAGE, INDEX_PAGE, DICTIONARY_PAGE, DATA_PAGE_V2
  2: required i32 uncompressed_page_size;     // 未压缩大小
  3: required i32 compressed_page_size;       // 压缩后大小
  4: optional i32 crc;                        // CRC32 校验
  5: optional DataPageHeader data_page_header;
  7: optional DictionaryPageHeader dictionary_page_header;
  8: optional DataPageHeaderV2 data_page_header_v2;
}
```

**性能问题与优化**：

parquet-rs 在 v57.0.0 中实现了自定义 Thrift 解析器，将 Footer 解析速度提升了 **3x ~ 9x**。主要优化包括：
- 避免传统 Thrift 生成代码的两步转换（Thrift struct -> API struct）
- 零拷贝解析字符串字段
- 减少内存分配次数

这说明 **Thrift 编码的 Footer 在大规模文件（数百列、数千 Row Groups）下存在解析性能瓶颈**。ForSt-RS 的 Footer 格式选择需要考虑这一点。

### 3.3 Bloom Filter (SBBF)

Parquet 使用 **Split Block Bloom Filter (SBBF)** 算法，这是一种 cache-friendly 且支持 SIMD 加速的 Bloom Filter 变体。

#### 3.3.1 Block 结构

SBBF 由 `z` 个 Block 组成，每个 Block 为 **256 bits = 8 x 32-bit words**：

```
Block (256 bits)
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ word 0 │ word 1 │ word 2 │ word 3 │ word 4 │ word 5 │ word 6 │ word 7 │
│ 32 bits│ 32 bits│ 32 bits│ 32 bits│ 32 bits│ 32 bits│ 32 bits│ 32 bits│
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
```

#### 3.3.2 核心操作

```
mask(x: u32) -> Block:
    对每个 word[i]:
        y = (x wrapping_mul SALT[i]) >> 27   // 取高 5 位 -> 0..31
        word[i] = 1 << y                     // 每个 word 恰好设 1 bit

block_insert(block, x: u32):
    m = mask(x)
    block[i] |= m[i]  // 对每个 word OR 运算

block_check(block, x: u32) -> bool:
    m = mask(x)
    return all(block[i] & m[i] != 0)  // 所有 word 的对应 bit 都已设置
```

#### 3.3.3 Filter 级操作

```
filter_insert(filter, x: u64):
    // 用高 32 位选择 block
    i = (x >> 32) * z >> 32         // 避免取模运算
    block_insert(filter.blocks[i], x as u32)

filter_check(filter, x: u64) -> bool:
    i = (x >> 32) * z >> 32
    return block_check(filter.blocks[i], x as u32)
```

#### 3.3.4 Hash 函数

使用 **xxHash (XXH64)** 函数，seed = 0，将任意 Parquet 类型的值映射为 64-bit hash。

#### 3.3.5 存储格式与位置

```thrift
struct BloomFilterPageHeader {
  1: required i32 numBytes;                   // bitset 大小（字节）
  2: required BloomFilterAlgorithm algorithm; // SBBF
  3: required BloomFilterHash hash;           // xxHash
  4: required BloomFilterCompression compression; // UNCOMPRESSED
}
```

Bloom Filter 数据**按 Column Chunk 粒度存储**，位置由 `ColumnMetaData.bloom_filter_offset` 指向。物理布局有两种：
1. 集中存储于所有 Row Groups 之后、Page Index 之前
2. 分散存储于各 Row Group 之间

#### 3.3.6 假阳性率与空间

| Bits per Insert | 假阳性率 |
|----------------|---------|
| 6.0 | 10% |
| 10.5 | 1% |
| 16.9 | 0.1% |
| 26.4 | 0.01% |
| 41 | 0.001% |

典型场景：1024 blocks、26214 个 hash 值时，假阳性率约 0.02%。

### 3.4 Page Index (Column Index + Offset Index)

Page Index 是 Parquet 较新引入的特性，旨在实现 **Page 级数据剪枝**，无需读取所有 Page Header 即可跳过不相关的 Page。

#### 3.4.1 Column Index

```thrift
struct ColumnIndex {
  1: required list<bool> null_pages;     // 标记纯 null page
  2: required list<binary> min_values;   // 每个 page 的 min 值
  3: required list<binary> max_values;   // 每个 page 的 max 值
  4: required BoundaryOrder boundary_order; // UNORDERED / ASCENDING / DESCENDING
  5: optional list<i64> null_counts;     // 每个 page 的 null 数量
  6: optional list<i64> repetition_level_histograms;
  7: optional list<i64> definition_level_histograms;
}
```

**用途**：
- 对**排序列**：可用 binary search 在 `min_values` / `max_values` 中定位匹配的 page，单行查找只需读 1 个 data page
- 对**非排序列**：顺序扫描 `min_values` / `max_values`，跳过不满足谓词的 page
- `boundary_order` 提示 Reader 选择搜索策略

**值截断优化**：Writer 可以截断过长的 min/max 值。例如，实际最小值为 "Blart Versenwald III"，Writer 可以存储 `min="B"`, `max="C"`，控制 Index 大小。

#### 3.4.2 Offset Index

```thrift
struct OffsetIndex {
  1: required list<PageLocation> page_locations;
}

struct PageLocation {
  1: required i64 offset;           // Page 在文件中的偏移
  2: required i32 compressed_page_size; // Page 压缩后大小（含 header）
  3: required i64 first_row_index;  // Page 第一行在 Row Group 中的行号
}
```

**用途**：
- 通过行号定位到具体 Page
- 结合 Column Index 使用：先通过 Column Index 确定哪些 Page 匹配谓词，再通过 Offset Index 获取 Page 的物理位置
- 跨列对齐：当一列的某些 Page 被跳过时，其他列的对应行也需跳过，通过 `first_row_index` 实现对齐

#### 3.4.3 存储位置

Page Index 存储在 **Row Group 数据之后、Footer 之前**，与 Footer 分离。这样 Reader 在不需要 page 级剪枝时可以跳过 Index 的 I/O 和反序列化开销。Index 的偏移和长度记录在 `ColumnChunk` 的 `offset_index_offset/length` 和 `column_index_offset/length` 字段中。

### 3.5 编码方式

Parquet 支持多种编码，目标是在不进行通用压缩的情况下最大化减少数据大小：

| 编码 | Enum | 支持类型 | 核心思路 |
|------|------|----------|---------|
| **PLAIN** | 0 | 所有类型 | 原生二进制，little-endian |
| **RLE_DICTIONARY** | 8 | 所有类型 | 字典页存唯一值 + 数据页存 RLE 编码的索引 |
| **RLE** | 3 | BOOLEAN, Dict Index | Run-Length Encoding + Bit-Packing 混合 |
| **DELTA_BINARY_PACKED** | 5 | INT32, INT64 | Delta 编码，header + blocks + miniblocks |
| **DELTA_LENGTH_BYTE_ARRAY** | 6 | BYTE_ARRAY | 长度 Delta 编码 + 数据拼接 |
| **DELTA_BYTE_ARRAY** | 7 | BYTE_ARRAY, FIXED_LEN | 前缀压缩（增量编码），适合排序字符串 |
| **BYTE_STREAM_SPLIT** | 9 | FLOAT, DOUBLE, INT32, INT64 | 按字节位置分流，提升后续压缩比 |

**关键设计**：

1. **Dictionary Encoding 是默认首选**：对大多数列，先尝试 Dictionary Encoding；当字典超过阈值（通常 1MB）时，后续 Page fallback 到 PLAIN
2. **编码与压缩分层**：编码先作用（减少数据量），压缩再作用（进一步压缩编码后的字节）
3. **DELTA_BYTE_ARRAY 适合排序数据**：对前缀相同的字符串序列（如排序后的 Key），可大幅减少存储
4. **BYTE_STREAM_SPLIT 不减少大小但改善压缩**：将浮点数的第 0 字节、第 1 字节分别聚集，使后续 Snappy/Zstd 更高效

### 3.6 压缩策略

Parquet 的压缩粒度为 **每个 Page**，支持以下 Codec：

| Codec | 特点 | 典型用途 |
|-------|------|----------|
| **UNCOMPRESSED** | 无压缩 | 已高度编码的数据 |
| **SNAPPY** | 最快的解压速度，中等压缩比 | 实时查询场景 |
| **GZIP** | 最高压缩比，较慢 | 批处理、冷数据 |
| **LZ4_RAW** | 极快压缩/解压，较低压缩比 | 高吞吐场景（推荐替代旧 LZ4） |
| **ZSTD** | 高压缩比 + 合理速度 | 通用推荐 |
| **BROTLI** | 高压缩比，较慢 | 网络传输优化 |
| **LZO** | 中等压缩比 | Hadoop 生态兼容 |
| **LZ4 (deprecated)** | 带非标准 framing，兼容性差 | **不推荐使用** |

**关键设计**：
- 压缩是 **per-column per-page** 的，不同列可以使用不同 Codec
- 每个 Page 独立压缩，支持随机访问任意 Page
- `PageHeader` 中同时记录 `uncompressed_page_size` 和 `compressed_page_size`，用于精确的 buffer 分配
- LZ4 的旧版本因 Hadoop 额外的 framing 导致跨实现兼容性差，这是一个教训

## 4. 对比表：Parquet vs ForSt-RS SST

| 维度 | Parquet | ForSt-RS SST (目标) | 借鉴/差异 |
|------|---------|---------------------|-----------|
| **定位** | OLAP 列式分析存储 | LSM-Tree KV 存储的 SSTable | Parquet 面向宽表分析；SST 面向 KV 点查/范围查 |
| **数据模型** | 嵌套 Schema，多列 | Key-Value 对，按 Key 排序 | SST 只有 2 列（Key, Value），且必须有序 |
| **Magic Bytes** | `"PAR1"` (头尾各 4 bytes) | 建议类似设计，头尾 magic 用于完整性校验 | 可直接借鉴 |
| **Footer 位置** | 文件末尾 | 文件末尾 | 完全借鉴：支持 single-pass 写入 |
| **Footer 编码** | Thrift TCompactProtocol | 建议使用 FlatBuffers 或自定义二进制 | Thrift 有解析性能问题（parquet-rs 3x~9x 优化佐证）；FlatBuffers 支持零拷贝 |
| **Footer 内容** | FileMetaData: Schema + RowGroup 列表 + 全局 KV 元数据 | SST Metadata: DataBlock 索引、Bloom Filter 偏移、统计信息 | SST Footer 更简单，无需嵌套 Schema |
| **数据组织** | Row Group -> Column Chunk -> Page (3 级) | DataBlock (Arrow RecordBatch) (1~2 级) | SST 不需要 Row Group 层；DataBlock 直接对应 Parquet 的 Page |
| **数据排序** | Row Group 内无序（可选排序列） | 全局按 Key 排序（LSM-Tree 要求） | SST 的全局有序是核心约束，可利用此特性优化索引 |
| **索引结构** | Column Index (min/max per page) + Offset Index | 稀疏索引 (每 Block 的 first key + offset) | Parquet 的 Column Index 相当于 SST 稀疏索引的超集；SST 因全局有序可用 binary search |
| **Bloom Filter** | SBBF per column chunk, xxHash, 256-bit block | Block 级 Bloom Filter | 可借鉴 SBBF 算法；SST 的 Bloom 粒度可以是 per-DataBlock 或全局 |
| **Bloom Filter Hash** | xxHash (XXH64, seed=0) | 建议同样使用 xxHash | 业界验证的高性能 hash |
| **编码** | Dictionary, RLE, Delta Binary Packed, Delta Byte Array, Byte Stream Split | Arrow 原生编码（Dictionary, RLE, 等） | Arrow IPC 格式自带 Dictionary Encoding；Delta 编码对排序 Key 特别有效 |
| **压缩** | Per-page, 支持 Snappy/LZ4_RAW/Zstd/Gzip/Brotli | Per-DataBlock | 可借鉴 per-block 压缩模式；Zstd 或 LZ4 为推荐选择 |
| **统计信息** | Per-ColumnChunk Statistics (min/max/null_count) + Per-Page Statistics (via Column Index) | Per-DataBlock min_key/max_key | SST 因只有 Key 列，统计信息更简单 |
| **Page 类型** | Data Page, Dictionary Page, Index Page | DataBlock (统一格式) | SST 不需要区分 Page 类型 |
| **Null 处理** | Definition Levels + Repetition Levels | Arrow 的 Validity Bitmap | Arrow 原生方案更高效 |
| **嵌套支持** | Dremel 编码（repetition/definition levels） | 不需要 | SST 的 KV 模型不涉及嵌套 |
| **加密** | 模块化加密（per-page, per-column, footer） | 暂不考虑 | 未来可选 |
| **校验** | Per-page CRC32 (optional) | 建议 per-DataBlock CRC32 | 直接借鉴 |

## 5. 与 ForSt-RS 重构的关系

### 5.1 可借鉴的设计要素

#### 5.1.1 Footer-at-end 模式 (高优先)

Parquet 的 "数据在前，Footer 在后" 模式是 SST 文件的标准做法。具体可借鉴的细节：
- **末尾固定大小的 trailer**：metadata length (4 bytes) + magic (4 bytes)，Reader 只需先读末尾 8 字节即可定位 Footer
- **Footer 包含所有 Block 的偏移信息**：避免顺序扫描定位数据

**建议**：ForSt-RS 使用类似结构：`[DataBlocks...][IndexBlock][BloomFilter][Footer][footer_length(4B)][magic(4B)]`

#### 5.1.2 SBBF Bloom Filter (高优先)

SBBF 算法的优势：
- **Cache-friendly**：每次查询只访问 1 个 256-bit block（一个 cache line）
- **SIMD 友好**：8 个 word 的 mask/check 可并行化
- **简单高效**：无需多个 hash 函数，单个 xxHash 值即可
- **parquet-rs 已有成熟实现**：可直接复用（`parquet::bloom_filter::Block`）

**建议**：ForSt-RS 直接采用 SBBF 算法，per-DataBlock 或全局建 Bloom Filter。使用 xxHash 作为 hash 函数。

#### 5.1.3 稀疏索引 + 统计信息 (高优先)

Parquet 的 Column Index / Offset Index 本质上就是 SST 稀疏索引的泛化版本：

| Parquet 概念 | ForSt-RS 对应 |
|-------------|--------------|
| Column Index min/max per page | 每个 DataBlock 的 first_key / last_key |
| Offset Index (offset + size + first_row_index) | 每个 DataBlock 的 (offset, size) |
| boundary_order = ASCENDING | 全局保证（SST 天然有序） |

**建议**：ForSt-RS IndexBlock 存储：`[(first_key, block_offset, block_size), ...]`，因为数据全局有序，查找时可用 binary search。

#### 5.1.4 Per-Block 压缩 (中优先)

Parquet per-page 压缩的优势：
- 支持随机访问（解压任意 Page 不依赖其他 Page）
- `PageHeader` 中记录 compressed/uncompressed size，精确分配 buffer

**建议**：ForSt-RS 每个 DataBlock 独立压缩，Footer/IndexBlock 中记录 compressed_size 和 uncompressed_size。推荐使用 **LZ4 或 Zstd**。

#### 5.1.5 Delta Byte Array 编码 (中优先)

对于排序的 Key 列，前缀压缩（Delta Byte Array / incremental encoding）可大幅减少存储。Parquet 的 `DELTA_BYTE_ARRAY` 编码正是为此设计。

**建议**：虽然 ForSt-RS 使用 Arrow RecordBatch 存储 DataBlock，但在 Key 列上可以考虑应用前缀压缩或 Dictionary Encoding。

#### 5.1.6 CRC 校验 (低优先)

Parquet 支持 per-page CRC32 校验。SST 文件在 LSM-Tree 场景下可能因存储介质错误导致数据损坏。

**建议**：ForSt-RS 为每个 DataBlock 计算 CRC32，存储在 IndexBlock 或 Block header 中。

### 5.2 不适用于 ForSt-RS 的设计

#### 5.2.1 Row Group 层级

Parquet 的 Row Group 是为 MapReduce 风格的并行处理设计的。SST 文件通常由单个线程顺序写入和读取，LSM-Tree 的并行性在文件层面（不同 SST 文件并行 compact）。ForSt-RS 不需要 Row Group 层级。

#### 5.2.2 Thrift 编码的 Footer

parquet-rs 的优化经验表明，Thrift 编码在大规模元数据解析时存在性能瓶颈。ForSt-RS 建议使用 **FlatBuffers**（零拷贝反序列化）或简单的自定义二进制格式。

#### 5.2.3 列式存储与嵌套编码

Parquet 的核心价值 -- 列式存储、列剪枝、Dremel 嵌套编码 -- 对 KV 存储不适用。ForSt-RS 的 "列" 是固定的 (key, value, sequence, type)，无需动态列投影。

#### 5.2.4 Dictionary Page

Parquet 的 Dictionary Encoding 在列级建立字典，适合高重复率的列。SST 的 Key 通常唯一（或接近唯一），Dictionary Encoding 对 Key 列效果有限。但对 Value 列可能有效，取决于业务数据特征。

#### 5.2.5 Column-per-Chunk Bloom Filter 粒度

Parquet 的 Bloom Filter 是 per-Column-Chunk 粒度（一个 Row Group 中某列的全部数据共用一个 Bloom Filter）。SST 因数据全局有序，更适合 **全局单一 Bloom Filter** 或 **per-DataBlock Bloom Filter**（类似 RocksDB 的做法）。

## 6. Open Questions

1. **Footer 编码选择**：FlatBuffers vs 自定义二进制 vs Protobuf？需要 benchmark 对比解析速度和空间开销
2. **Bloom Filter 粒度**：全局 SBBF vs per-DataBlock SBBF？全局节省空间但失去 Block 级过滤能力；per-Block 增加空间但可以精确定位
3. **Key 编码**：是否在 Arrow RecordBatch 的 Key 列上额外应用前缀压缩？还是依赖 Arrow 的 Dictionary Encoding + 通用压缩？
4. **压缩算法**：Zstd 在压缩比和速度之间取得了很好的平衡，但 LZ4 在解压速度上更优。SST 的 read-heavy 特性是否应优先考虑解压速度？
5. **parquet-rs SBBF 复用**：是否直接依赖 `parquet` crate 的 Bloom Filter 实现？还是独立维护以减少依赖？（参见 [arrow-rs#8277](https://github.com/apache/arrow-rs/issues/8277)，Lance 社区也有此诉求）
6. **Page Index 是否需要**：SST 的全局有序特性使得稀疏索引 + binary search 已经很高效，是否还需要类似 Column Index 的 min/max 统计？对于范围查询，稀疏索引的 first_key 已足够定位起始 Block
