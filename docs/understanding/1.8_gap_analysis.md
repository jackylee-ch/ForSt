## 1. Context

本文档基于 Wave 1 的 9 份分析文档（1.1-1.6, 1.9-1.11），对照 ForSt-RS 的 13 项核心要求（R1-R13），系统性地梳理现状与目标之间的差距。每项要求均从前置文档中提取源码证据和架构发现，给出差距评估、实现难度和优先级建议。

**评估维度说明**:
- **难度** H=高 / M=中 / L=低 — 衡量工程实现的复杂度和风险
- **优先级** P0=阻塞性必须 / P1=核心功能 / P2=增强优化

## 2. Gap 矩阵

### R1: 流式场景适配

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 基于 RocksDB 通用 LSM-Tree 引擎，核心读/写路径（WriteImpl/GetImpl）与 RocksDB 完全一致（文档 1.2 第 3.8 节）。Flink 差异仅在环境适配层（Env/FileSystem），通过 JNI 桥接 Flink FileSystem。引擎本身未针对流式场景（高频 key 更新、低延迟点查）做特殊优化。Fluss 侧每个 KvTablet 使用独立 RocksDB 实例+单默认 ColumnFamily（文档 1.10 第 3.1.3 节），存在资源碎片化问题。 |
| **目标** | 面向流式的 key 更新/点查优化：减少写放大、降低点查延迟、优化 Compaction 对前台操作的干扰。共享存储引擎实例以降低资源碎片化。 |
| **Gap** | 1) 写路径的 WriteGroup + WAL 串行瓶颈（文档 1.2 第 3.2 节），对高频小批次写入不友好；2) 读路径的 MemTable → Immutable MemTable → Level 0..N 多层查找在流式点查场景下延迟过高；3) 通用 Compaction 策略（Level/Universal/FIFO）未针对流式 key 更新的"大量相同 key 重复写"场景做优化；4) 每 bucket 独立 RocksDB 实例导致数千 bucket 下大量内存浪费和系统调用开销（文档 1.10 第 3.8.2 节第 1 项）。 |
| **难度** | **H** — 需重新设计存储引擎内核，涉及 MemTable、Compaction、资源共享等核心模块 |
| **优先级** | **P0** — 流式场景适配是 ForSt-RS 存在的根本理由 |

---

### R2: 数据向量化

| 维度 | 内容 |
|------|------|
| **现状** | ForSt/RocksDB 的数据传输单元是 `byte[]`/`Slice`，逐条处理 KV 对。Flink 异步状态后端虽然已实现批量 `multiGetAsList()` 和 `WriteBatch`（文档 1.4 第 3.3 节），但底层仍是逐条序列化/反序列化。Fluss 已大量使用 Arrow 列式格式（ArrowWriter、ArrowWalBuilder、MemoryLogRecordsArrowBuilder），WAL 采用 Arrow IPC RecordBatch 编码（文档 1.10 第 3.2 节），并且已实现自定义的 ChunkedAllocationManager 进行 off-heap 内存管理（文档 1.9 第 2.1.1 节）。 |
| **目标** | 存储引擎原生支持 Arrow RecordBatch 作为数据传输单元，批量读写操作直接操作列式数据，消除逐条 byte[] 序列化/反序列化开销。 |
| **Gap** | 1) RocksDB/ForSt 的核心 API（Get/Put/Iterator）全部基于 byte[] Slice，无列式数据接口；2) Flink ForSt 状态后端的 `ForStInnerTable.serializeKey()`/`deserializeValue()` 仍是逐条字节操作（文档 1.4 第 3.4.4 节）；3) Fluss WAL 层虽已使用 Arrow，但 KV 存储层（RocksDB）仍是行式 byte[]；4) Arrow RecordBatch 与 LSM-Tree 的 DataBlock 集成方案尚未设计（文档 1.11 第 4 节对比表指出 SST DataBlock 应对应 Arrow RecordBatch）。 |
| **难度** | **H** — 需重新设计存储引擎的数据表示层，从 Slice 转为 Arrow RecordBatch；SST 文件格式需要完全重新设计 |
| **优先级** | **P0** — 向量化是获取性能飞跃的基础 |

---

### R3: IO 向量化

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 使用传统的同步 `read()`/`write()` 系统调用。文件 IO 通过 `FileSystem` 抽象（POSIX 或 Flink FileSystem），Flink 环境下每次 IO 还需跨越 JNI 边界（文档 1.2 第 3.7 节）。`RandomAccessFileReader`、`WritableFileWriter` 等封装提供了预读缓冲（文档 1.1 第 3.1 表模块 10 `file/`），但底层仍是标准 POSIX IO。Fluss 的 LogSegment 也使用传统文件通道（文档 1.10 第 3.4 节）。ArrowWalBuilder 存在 `nioBuffer()` 深拷贝问题（文档 1.10 第 3.8.2 节第 2 项）。 |
| **目标** | 使用 io_uring + vectored IO（scatter-gather）实现异步非阻塞 IO，消除系统调用开销和线程上下文切换。 |
| **Gap** | 1) 整个 ForSt C++ 引擎的 IO 路径基于同步 POSIX API，无 io_uring 支持；2) Flink 环境的文件 IO 需跨越 JNI → C++ → JNI 双重边界（文档 1.3 第 3.3 热路径 4/5）；3) 无 scatter-gather IO 支持，ArrowWalBuilder 需将分页内存合并为连续缓冲区才能写入（文档 1.10 第 3.7.2 节）；4) Compaction 的 IO pipeline 完全同步（文档 1.2 第 3.6.4 节）。 |
| **难度** | **M** — Rust 生态有成熟的 io_uring 库（tokio-uring），主要工作在集成设计和 IO 调度 |
| **优先级** | **P1** — IO 向量化带来显著的吞吐提升，但需在基础存储引擎完成后实施 |

---

### R4: 计算向量化

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 使用标量运算处理所有计算（hash、CRC32、key 比较、Bloom Filter 检查等）。C++ 编译器可能自动向量化部分循环，但无手动 SIMD 优化（文档 1.1 第 3.1 模块 13 `util/`：hash/CRC32/coding 等底层工具）。Java 侧的 JDK Vector API 仍处于 Incubator 阶段（第十次，文档 1.9 第 3.8 节），不适合生产使用。Parquet 的 SBBF Bloom Filter 设计天然 SIMD 友好（8x32-bit word 并行，文档 1.11 第 3.3 节）。 |
| **目标** | 在关键计算路径（hash、CRC32、key 比较、Bloom Filter、编码/解码）使用 SIMD 内核加速。 |
| **Gap** | 1) ForSt C++ 代码无手动 SIMD 优化路径；2) Java 侧 Vector API 不成熟，无法依赖；3) SBBF Bloom Filter 的 SIMD 实现需要在 Rust 侧完成；4) arrow-rs 已有部分 auto-vectorization 和手动 SIMD 计算内核（文档 1.9 第 3.8.4 节），但与 ForSt-RS 存储引擎的集成路径未设计。 |
| **难度** | **M** — Rust 有良好的 SIMD intrinsics 支持（`std::arch`），且 arrow-rs 已有参考实现；关键在识别热点并实现 |
| **优先级** | **P2** — 属于性能调优阶段，不阻塞核心功能 |

---

### R5: 加速策略

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 继承 RocksDB 的标准加速机制：1) Bloom Filter（BlockBasedTable 内置，文档 1.2 第 3.3 阶段 4）；2) Block Cache（LRU 和 HyperClockCache 两种实现，文档 1.2 第 3.5 节）；3) 稀疏索引（Level 文件内二分查找，文档 1.2 第 3.1.3 节 VersionSet）。ForSt 的 HyperClockCache 已采用无锁 CLOCK 算法（文档 1.2 第 3.5.2 节），适合 Flink 高并发点查。Fluss 的 RemoteLogIndexCache 使用 Caffeine LFU（文档 1.10 第 3.5.5 节）。 |
| **目标** | 增强 Bloom Filter（SBBF 算法 + SIMD）、多级索引（稀疏索引 + Block 级 min/max 统计）、分层缓存（Heap → NVMe → 远端）。 |
| **Gap** | 1) 当前 Bloom Filter 是 RocksDB 传统实现，非 SBBF；SBBF 的 cache-friendly 和 SIMD 友好特性未利用（文档 1.11 第 3.3 节分析）；2) Block Cache 仅支持内存层，无 NVMe SSD 二级缓存（CompressedSecondaryCache 虽存在但仅内存中压缩存储，文档 1.2 第 3.5.3 节）；3) 缺少 Block 级 min/max 统计信息（类似 Parquet Column Index），需依赖 Arrow SST 的自定义 Footer 实现（文档 1.11 第 5.1.3 节）；4) ForSt 的 FileBasedCache（文档 1.6 第 3.2 节）提供了文件级 LRU 缓存，但仅用于远程文件系统的 SST 缓存，非通用 Block 级分层缓存。 |
| **难度** | **M** — SBBF 可复用 parquet-rs 实现；分层缓存需设计但有成熟参考；统计信息需与 SST 格式协同 |
| **优先级** | **P1** — 加速策略直接影响读取延迟，是流式点查的核心竞争力 |

---

### R6: 双轨兼容（Sync + Async）

| 维度 | 内容 |
|------|------|
| **现状** | Flink 2.2 已实现完整的双轨状态后端：1) **同步路径**：`ForStSyncKeyedStateBackend extends AbstractKeyedStateBackend`，使用 State v1 API，单线程 `db.get()`/`db.put()`（文档 1.4 第 3.5 节）；2) **异步路径**：`ForStKeyedStateBackend implements AsyncKeyedStateBackend`，使用 State v2 API，多线程批量 `multiGetAsList()`/`WriteBatch`（文档 1.4 第 3.3 节）。两条路径分别通过不同的接口继承链实现，共享底层 RocksDB 实例但执行模式完全不同。 |
| **目标** | 统一的 FFM/JNI 后端同时支持同步和异步两条路径，保持 Flink 2.2 双轨 API 的完全兼容。 |
| **Gap** | 1) 当前两条路径的 Java 层代码独立（`sync/` 包 vs 主包），但底层 JNI 调用相同（文档 1.4 第 3.5 表）；2) ForSt-RS 替换 JNI 后端后，需要同时满足同步（单线程阻塞调用）和异步（多线程批量调用）两种执行模式；3) 异步路径的 `ForStStateExecutor` 使用 coordinator+read+write 三组线程池（文档 1.4 第 3.3.1 节），Rust 侧需提供线程安全的并发访问；4) 同步版是否在 ForSt-RS 中保留是一个开放问题（文档 1.4 Open Questions 第 6 点）。 |
| **难度** | **M** — Java 层的双轨代码可大量复用；Rust 侧需确保 API 同时满足单线程和多线程并发安全 |
| **优先级** | **P0** — 双轨兼容是 Flink 集成的基本要求 |

### R7: FFM 替代 JNI

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 通过 JNI 将 C++ 引擎暴露给 Java，共 ~1461 个 native 方法（文档 1.3 第 1 节）。核心热路径的数据拷贝开销严重：`get()` 3 次拷贝、`multiGet` N*3 次拷贝、`put()` 2 次拷贝（文档 1.3 第 3.3 节）。虽然 DirectByteBuffer 变体已存在（`putDirect`/`getDirect` 等），将拷贝降至 0-1 次（文档 1.3 第 5.3 节），但 JNI 本身仍有调用开销（~56.6ns，文档 1.9 第 3.7.1 节）。内存生命周期通过 `RocksObject.nativeHandle_` + `AtomicBoolean owningHandle_` 手动管理，存在 use-after-close、双重释放等风险（文档 1.3 第 3.4.3 节）。 |
| **目标** | 使用 FFM（Foreign Function & Memory API，JDK 22+ final）替代 JNI：1) 零拷贝数据传递（MemorySegment 直接映射原生内存）；2) 更安全的生命周期管理（Arena scope）；3) 更低的调用开销（~22.7ns，比 JNI 快 ~60%）。 |
| **Gap** | 1) FFM API 需要 JDK 22+，而 Fluss 当前要求 Java 8 源码兼容（文档 1.9 第 3.9 限制 1）；2) 需要设计双模式桥接层：JDK < 22 使用 JNI，JDK >= 22 使用 FFM（文档 1.9 第 5.1 节建议的 Phase 0/Phase 1 路径）；3) Fluss 使用 shaded Arrow，需验证 C Data Interface 结构体的二进制兼容性（文档 1.9 第 3.9 限制 2）；4) 跨语言引用计数协调机制需要设计（文档 1.9 第 3.9 限制 4）；5) 当前 ~1461 个 native 方法中大量是 Options getter/setter（~530 个），属于配置操作（文档 1.3 第 3.1.4 节），可保持 JNI 不影响性能。 |
| **难度** | **H** — JDK 版本兼容策略复杂；需维护 JNI + FFM 双桥接层；引用计数协调跨语言有风险 |
| **优先级** | **P1** — 近期可先用 JNI + 指针传递实现零拷贝（参考 DataFusion Comet），FFM 作为渐进式升级 |

### R8: 远端对象存储

| 维度 | 内容 |
|------|------|
| **现状** | 在 bmr-2.1.0 分支中，**不存在**完整的存算分离/远端对象存储实现（文档 1.6 第 3.1 节：搜索 `ForStDisagg`/`DisaggState`/`remote.state`/`object.store`/`bos.endpoint` 均未找到）。但已存在关键基础设施：1) ForStFlinkFileSystem 支持通过 JNI 桥接远程文件系统（S3/HDFS/OSS）（文档 1.2 第 3.7.1 节）；2) FileBasedCache 文件级 LRU 缓存（文档 1.6 第 3.2 节）；3) FileOwnership 三级所有权模型（文档 1.6 第 3.3.2 节）；4) `ForStOptions.SYNC_ENFORCE_LOCAL` 配置描述中预留了 disaggregated state 概念。Fluss 的 RemoteLogStorage 已支持 FileSystem 抽象的远程日志存储（文档 1.10 第 3.5 节）。 |
| **目标** | ForSt-RS 原生支持 BOS/S3 等对象存储作为 SST 文件的持久化层，无需通过 JNI → Flink FileSystem 的间接路径。 |
| **Gap** | 1) 当前远程文件系统访问必须经过 JNI → FlinkFileSystem → Java FileSystem 的多层间接，每次 IO 跨两次语言边界（文档 1.2 第 3.7 节、文档 1.3 热路径分析）；2) 无 Rust native 的对象存储客户端集成；3) 存算分离的运行时管理器（StateTransferManager、ConsistencyProtocol）需从零构建（文档 1.6 第 5.2 节）；4) SST 文件的所有权转移（DB → JM）机制需适配 Rust 引擎（文档 1.6 第 3.3 节 FileOwnership）；5) 远程 IO 的延迟特性（100ms+ 级别）与 LSM-Tree 的本地 IO 假设存在根本冲突，需要缓存和预取策略。 |
| **难度** | **H** — 需设计完整的远端存储抽象、Rust native 对象存储客户端、缓存/预取策略、一致性协议 |
| **优先级** | **P1** — 存算分离是云原生部署的基础，但可分阶段实施：先本地 Rust 引擎，再远端存储 |

### R9: 冷热分层

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 的 Block Cache 仅支持内存层：LRU Cache（分片 Mutex）和 HyperClockCache（无锁 CLOCK），均为内存缓存（文档 1.2 第 3.5 节）。CompressedSecondaryCache 存在但也是内存中的压缩缓存（文档 1.2 第 3.5.3 节）。RocksDB 的 `TieredSecondaryCache` 提供了多级缓存框架但 ForSt 未见使用证据。ForSt Flink 端的 FileBasedCache（文档 1.6 第 3.2 节）实现了"热区（本地磁盘）+ 冷区（元数据保留但文件已删除）"的两段式 LRU，但这是文件粒度缓存，非 Block 粒度。 |
| **目标** | 三级缓存层次：Heap（热数据，Block 级）→ NVMe SSD（温数据，Block/File 级）→ Object Store（冷数据，SST 文件级）。 |
| **Gap** | 1) 缺少 NVMe SSD 缓存层——当前 Block Cache 淘汰后直接回退到远程 IO；2) FileBasedCache 的两段式 LRU 算法可复用（文档 1.6 第 5.1 节），但需从文件粒度细化到 Block 粒度；3) 缓存容量策略（SizeBasedCacheLimitPolicy + SpaceBasedCacheLimitPolicy，文档 1.6 第 3.2.4 节）可借鉴但需适配三级架构；4) 热/温/冷数据的自动迁移策略需设计；5) NVMe 直接 IO 路径（绕过 OS Page Cache）需在 Rust 侧实现。 |
| **难度** | **M** — 概念清晰、有参考实现（RocksDB TieredSecondaryCache、ForSt FileBasedCache），实现工作量中等 |
| **优先级** | **P1** — 冷热分层是存算分离场景下读取性能的关键保障 |

### R10: Checkpoint 集成

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 的 Checkpoint 体系已完善：1) **增量快照**（默认）：`ForStIncrementalSnapshotStrategy` 通过 `db.disableFileDeletions()` + `db.getLiveFiles()` 获取活跃文件列表，SST 文件差分追踪通过 `PreviousSnapshot` 实现，仅上传新增 SST（文档 1.5 第 3.2 节）；2) **全量快照**：`ForStNativeFullSnapshotStrategy`，所有文件上传（文档 1.5 第 3.3 节）；3) **恢复操作**：`ForStIncrementalRestoreOperation` 支持最佳 handle 选择、并行下载、Scale-in/out（文档 1.5 第 3.4 节）；4) **零拷贝 Checkpoint**：`ReusableDataTransferStrategy` 在远程 FS 下通过句柄传递实现零拷贝（文档 1.5 第 3.5.4 节）；5) **文件缓存**：FileBasedCache 加速远程 SST 读取（文档 1.5 第 3.5.5 节）。Fluss 侧的 KV 快照使用 RocksDB 原生 Checkpoint + SST 增量去重 + 并行上传（文档 1.10 第 3.6 节）。 |
| **目标** | Rust 引擎提供等价的 Checkpoint/Restore 接口，适配 Flink 增量/全量快照策略和 Fluss KV 快照机制。 |
| **Gap** | 1) 增量快照依赖 RocksDB 原生的 `disableFileDeletions()`/`getLiveFiles()`/`Checkpoint.create()` API（文档 1.5 第 3.2 节），Rust 引擎需实现等价的 SST 文件生命周期管理接口；2) `PreviousSnapshot` 的 SST 差分追踪逻辑（pruneFirstCheckpointSstFiles 剪枝，文档 1.5 第 3.2 节）可在 Java 层复用，但 Rust 引擎需暴露 SST 文件列表；3) Restore 过程中的 `clipDBWithKeyGroupRange`（deleteFilesInRanges + deleteRange，文档 1.5 第 3.4 节）需要 Rust 引擎支持；4) `IngestDB` 模式用于 Scale-in/out 快速恢复（文档 1.5 第 3.4 节），Rust 引擎需支持外部 SST 导入；5) Fluss 的 `RocksIncrementalSnapshot` 直接调用 RocksDB Checkpoint API（文档 1.10 第 3.6.1 节），替换后需适配。 |
| **难度** | **H** — Checkpoint 涉及引擎内部的文件管理、一致性快照、增量追踪等深层能力，是引擎替换的核心风险点 |
| **优先级** | **P0** — Checkpoint 是 Flink/Fluss 容错的基础，必须在首版即支持 |

### R10.5: 内部元数据（MANIFEST）

| 维度 | 内容 |
|------|------|
| **现状** | ForSt/RocksDB 使用 C++ MANIFEST 文件管理 SST 文件元数据：`VersionSet` 维护所有 `Version` 的链表，通过 `VersionEdit` 增量更新（文档 1.2 第 3.1.3 节）。MANIFEST 文件是 Checkpoint 的关键组成部分——增量快照中 MANIFEST 文件需要单独传输（文档 1.5 第 3.2 节异步阶段），恢复时需解析 MANIFEST 获取 ColumnFamily 描述符（文档 1.5 第 3.4 节）。Fluss 的 RemoteLogManifest 使用不可变 JSON 格式 + Copy-on-Write 策略（文档 1.10 第 3.5.4 节）。 |
| **目标** | ForSt-RS 的内部元数据管理需要选择一种模式：A) 沿用 RocksDB MANIFEST 格式（兼容但受限）；B) 设计 Rust 原生的 MANIFEST 格式（灵活但不兼容）；C) 混合模式（读兼容旧格式，写新格式）。 |
| **Gap** | 1) 模式 A 需要 Rust 引擎能读写 RocksDB MANIFEST 的二进制格式（ProtoBuf 编码的 VersionEdit），实现复杂且永远受限于 RocksDB 的设计决策；2) 模式 B 获得设计自由（可采用 FlatBuffers 零拷贝序列化，参考文档 1.11 第 5.2.2 节对 Thrift 性能问题的分析），但丧失与现有 Checkpoint 的兼容性；3) 模式 C 最灵活但工程量最大；4) 决策影响 Checkpoint 格式兼容性——如果 MANIFEST 格式变更，现有的增量 Checkpoint 恢复路径需适配；5) Fluss 的 RemoteLogManifest 的不可变 Copy-on-Write 设计（文档 1.10 第 3.8.1 节第 4 项）可作为设计参考。 |
| **难度** | **H** — 设计决策影响深远，涉及格式兼容性、Checkpoint 交互、迁移策略等多个维度 |
| **优先级** | **P0** — 元数据管理方案必须在引擎设计初期确定 |

### R11: SST 格式

| 维度 | 内容 |
|------|------|
| **现状** | ForSt 使用 RocksDB 的 BlockBasedTable 作为 SST 格式（文档 1.1 第 3.1 表模块 5 `table/`：~126 源文件）。该格式以固定大小的 Block（默认 4KB）为基本单元，Block 内按 key 排序并使用前缀压缩。SST 文件包含 Data Block、Meta Block（Bloom Filter）、Meta Index Block、Index Block 和 Footer（文档 1.2 读路径描述）。该格式设计成熟但面向通用 KV 场景，非列式存储。 |
| **目标** | 设计基于 Arrow RecordBatch 的自定义 SST 格式：DataBlock 为 Arrow RecordBatch（key/value/sequence/type 列），Footer 采用 FlatBuffers 零拷贝序列化，索引支持稀疏索引 + Block 级 min/max 统计 + SBBF Bloom Filter。 |
| **Gap** | 1) BlockBasedTable 的 ~126 个源文件是 RocksDB 最复杂的模块之一，短期内通过 C FFI 复用更现实（文档 1.1 第 5.2 节）；2) Arrow-based SST 的物理布局需完全重新设计——文档 1.11 已给出详细的对比分析和建议：Footer-at-end 模式（第 5.1.1 节）、SBBF Bloom Filter（第 5.1.2 节）、稀疏索引（第 5.1.3 节）、per-block 压缩（第 5.1.4 节）；3) 需解决 Arrow RecordBatch 与 KV 排序的适配——SST 要求全局按 Key 排序，Arrow 的列式布局需在此约束下设计；4) Delta Byte Array 编码对排序 Key 列的前缀压缩效果好（文档 1.11 第 5.1.5 节），但与 Arrow 原生编码的集成需评估；5) 格式变更意味着现有 RocksDB SST 文件不可直接被新引擎读取，需迁移策略。 |
| **难度** | **H** — 核心存储格式的重新设计，影响引擎的所有读写路径；需要大量设计、实现和测试工作 |
| **优先级** | **P0** — SST 格式是存储引擎的核心，决定了数据组织和性能特征 |

### R12: Flink 场景完整性

| 维度 | 内容 |
|------|------|
| **现状** | Flink 2.2 的 ForSt 状态后端支持 5 种状态类型（ValueState、ListState、MapState、ReducingState、AggregatingState），每种都有完整的 get/put/clear 语义（文档 1.4 第 3.2 节）。关键场景：1) 批量读（multiGetAsList）和批量写（WriteBatch）已实现（文档 1.4 第 3.4.2/3.4.3 节）；2) 迭代器用于 MapState 前缀扫描（文档 1.4 第 3.2.4 节）；3) TTL 通过 FlinkCompactionFilter 在 Compaction 时清理过期状态（文档 1.1 第 3.2.2 节）；4) ListState 使用 Merge Operator（StringAppendOperator）高效 append（文档 1.4 第 3.2.3 节）；5) Checkpoint 包括增量/全量快照（文档 1.5）。Fluss 侧的 KV 场景覆盖了 PK 表的 CRUD + CDC + Snapshot + Remote Tiering（文档 1.10）。 |
| **目标** | ForSt-RS 完整覆盖所有 P0/P1/P2 Flink 状态场景，包括 5 种状态类型、双轨执行、Checkpoint/Restore、TTL、Merge Operator、PriorityQueue（Timer Service）。 |
| **Gap** | 1) **Merge Operator 兼容性**：ListState 依赖 RocksDB 的 StringAppendOperator（文档 1.4 Open Questions 第 2 点），Rust 引擎需实现等价的 merge 语义；2) **TTL Compaction Filter**：`FlinkCompactionFilter`（文档 1.1 第 3.2.2 节）在 Compaction 时检查 TTL 时间戳清除过期 entry，Rust 引擎的 Compaction 需支持等价的 filter 插件；3) **PriorityQueue**：Flink Timer Service 依赖 `PriorityQueueSetFactory`（文档 1.4 第 3.6.1 节），需 Rust 引擎支持或在 Java 层独立实现；4) **状态迁移**：异步版 ForSt 的状态迁移（序列化器变更）尚未完全实现（文档 1.4 Open Questions 第 5 点："TODO: 2024/6/6 - Implement state migration"）；5) **Native Metrics**：`ForStNativeMetricMonitor` 直接读取 RocksDB 内部统计信息（文档 1.4 Open Questions 第 4 点），Rust 引擎需暴露等价指标；6) 最小 JNI 边界操作集为 12 个核心 DB 操作（文档 1.4 第 3.6.4 节），全部需实现。 |
| **难度** | **H** — 场景覆盖面广，每个子场景（Merge/TTL/PriorityQueue/Metrics/Migration）都有独立复杂度 |
| **优先级** | **P0** — Flink 场景完整性是 ForSt-RS 能否替换 ForSt 的验收标准 |

### R13: Fluss 场景完整性（补充项）

| 维度 | 内容 |
|------|------|
| **现状** | Fluss 在存储层使用 RocksDB 作为 KvTablet 的底层引擎（文档 1.10 第 3.1 节），涉及：1) KvPreWriteBuffer + RocksDB 的 WAL-first 一致性模型；2) 四种 RowMerger 策略（Default/FirstRow/Versioned/Aggregate）；3) RocksDB 增量快照 + SST 文件去重 + 并行上传；4) 两阶段恢复（HW 前直接写 RocksDB，HW 后写 PreWriteBuffer）；5) Arrow WAL 格式（ArrowWalBuilder + MemoryLogRecordsArrowBuilder）。 |
| **目标** | ForSt-RS 完整替换 Fluss 的 RocksDB 依赖，保持所有 KV 操作语义不变。 |
| **Gap** | 1) RocksDB 的 WAL 被禁用（Fluss 有自己的 WAL 机制，文档 1.10 第 3.1.3 节），Rust 引擎可简化此部分；2) 单默认 ColumnFamily 策略需评估是否在 Rust 引擎中改进（文档 1.10 第 3.8.2 节建议共享实例+多 CF）；3) `RocksIncrementalSnapshot` 直接调用 RocksDB Checkpoint API，替换后需 Rust 引擎提供等价 API（文档 1.10 第 3.6.1 节）；4) KvRecoverHelper 的两阶段恢复直接操作 RocksDB（文档 1.10 第 3.6.3 节），需适配新引擎接口。 |
| **难度** | **M** — Fluss 对 RocksDB 的使用相对简单（单 CF、无 WAL、基本 Get/Put），比 Flink 场景简单 |
| **优先级** | **P1** — Fluss 是 ForSt-RS 的重要应用场景，但可在 Flink 集成之后实施 |

## 5. 风险点

| 风险 | 影响 | 缓解策略 |
|------|------|---------|
| SST 格式不兼容导致无法滚动升级 | 现有数据需全量迁移 | 设计 SST 格式转换工具；过渡期支持读旧格式 |
| Checkpoint 语义不一致导致状态丢失 | 生产环境数据丢失 | 全面的 Checkpoint 一致性测试；与 ForSt 的 A/B 对比测试 |
| FFM/JNI 桥接层的内存泄漏 | 长时间运行后 OOM | 跨语言引用计数的自动化测试；泄漏检测工具集成 |
| Merge Operator 语义不完全等价 | ListState 数据损坏 | 基于 ForSt 测试用例构建 Rust 侧回归测试 |
| JDK 版本约束（Java 8 源码级别） | FFM 路径受限 | 独立 bridge 模块 + 运行时检测（文档 1.9 第 3.9 节方案） |

## 6. Open Questions

1. **ForSt-RS Phase 1 的最小可行范围**：是否可以先不实现自定义 SST 格式（R11），而是通过 Rust FFI 调用 RocksDB C API 实现初版引擎？这样可以更快验证双轨兼容（R6）和 Checkpoint 集成（R10）。
2. **MANIFEST 格式决策的时间窗口**：R10.5 的 A/B/C 三种模式各有利弊，是否需要专门的设计文档和评审来确定方向？
3. **Flink 社区对 ForSt-RS 的接受度**：ForSt-RS 是否需要以 FLIP 的形式提交到 Flink 社区？这会影响 API 设计的约束和时间线。
4. **性能基线**：是否需要先建立当前 ForSt + JNI 的性能基线（吞吐、延迟、内存），作为 ForSt-RS 的对比参照？
