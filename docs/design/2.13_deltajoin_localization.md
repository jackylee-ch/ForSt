## 1. 架构概述

### 1.1 设计目标

ForSt-RS 作为嵌入式存储引擎直接运行于 Flink TaskManager 进程内，**仅在 DeltaJoin 场景下替代 Fluss 的 Lookup 角色**。上游 changelog 数据经 Flink DataStream 管道流入 ForSt-RS，DeltaJoin Operator 通过本地 prefix_scan 完成维表查询——**零 RPC、零 JNI**（通过 FFM/C ABI 直接调用 Rust 层）。

> **范围说明**: ForSt-RS 仅替代 Fluss 在 DeltaJoin Lookup 路径上的角色（本地化维表查询），不替代 Fluss 作为通用共享存储、CDC 订阅、跨引擎查询等能力。Fluss 可继续作为维表数据的持久化源和 CDC 供应者。

核心架构特征：
- **本地无状态**：本地不持有持久化状态，仅保留热点 Cache 数据（BlockCache + SSD Cache）；所有持久化数据（SST 文件）存储在远端（S3/HDFS）
- **远端数据合并**：Remote Merge Service 在远端执行 SST 合并与 Compaction，TaskManager 本地资源消耗最小化
- **快速恢复**：由于本地无状态，作业重启或 Rescaling 时无需恢复本地数据——仅需从远端 blob 恢复 VersionSet 元数据（<10ms），BlockCache 逐步预热
- **嵌入式引擎**：ForSt-RS 嵌入 Flink TaskManager，无需外部存储服务
- **本地 Lookup**：DeltaJoin Operator 直接在本地 ForSt-RS 上执行 prefix_scan，消除网络往返
- **通用数据源**：上游 changelog 来自任意 Flink Source（Kafka、数据库 CDC 等），经 DataStream 管道写入 ForSt-RS

### 1.2 核心决策

| 维度 | 设计选择 | 理由 |
|------|---------|------|
| 存储引擎 | ForSt-RS 嵌入 Flink TM | 零 RPC、零 JNI，本地 prefix_scan |
| 本地状态策略 | **无状态** — 仅热点 Cache | 快速恢复、零状态迁移开销 |
| 调用方式 | FFM/C ABI | 避免 JNI 开销，Java 22+ 优先，JNI 降级兜底 |
| 数据摄入 | Flink DataStream 管道 | 通用 changelog 源，ForSt-RS 自主管理全生命周期 |
| 远端持久化 | SST 直写 S3/HDFS | 对齐社区 ForSt 存储模型 |
| 多维表合并 | Remote Merge Service | SST 级别合并，单 ForSt-RS 实例读取统一视图 |

### 1.3 整体数据流

```
上游 changelog (Kafka / CDC / 任意 Source)
  → Flink DataStream 管道
    → ForStRsDeltaJoinSource (数据摄入算子)
      → ForSt-RS Engine.batch_write()
        → MemTable → Flush → SST 直写 S3

DeltaJoin Operator
  → ForStRsLocalLookupFunction
    → ForSt-RS Engine.prefix_scan() (FFM/C ABI, 零 RPC)
      → MemTable + BlockCache + SSD Cache + S3
    → Arrow RecordBatch 零拷贝返回
  → JoinedRowData 拼装 → Sink
```

## 2. 存储分层模型

### 2.1 核心原则

ForSt-RS 的 DeltaJoin 存储模型遵循 **"本地无状态、远端持久化、热点缓存"** 原则：
- **SST 文件直接写入远端存储**（S3/HDFS），通过 FileSystem 抽象层（非先写本地再上传）
- **本地仅作为热点缓存层**（BlockCache + SSD Cache），不持有持久化状态数据
- **MemTable 是唯一的本地可写结构**，但其数据在 Flush 后即持久化到远端，本地 MemTable 为临时缓冲区
- **Checkpoint 零拷贝**：SST 已在远端，只需转移 ownership（handle 元数据）
- **作业恢复无需本地状态迁移**：远端 SST + blob 元数据即可完整恢复，本地 Cache 逐步预热

### 2.2 存储分层

```
ForSt-RS 本地 (Flink TaskManager) — 无持久化状态
  ├── MemTable (活跃写入, 内存, 临时缓冲区)
  │    └── batch_write → freeze → flush → SST 直写 S3 (flush 后本地释放)
  ├── VersionSet (内存元数据, 从远端 blob 恢复)
  ├── L1 BlockCache (热点 SST Block, 内存, ShardedClock)
  │    └── 256MB-4GB, <1us
  └── L2 SSD Cache (温热 SST Block, NVMe SSD, 可选)
       └── 10-100GB, 10-100us

ForSt-RS 远端 (S3/HDFS, primary-dir) — 全量持久化
  └── 全量 SST 文件 (共享存储)
       ├── Flush: MemTable → SST → 直接写远端
       ├── Compaction: 输入 SST (远端读) → 输出 SST (远端写)
       ├── Checkpoint blob: VersionSet + Frozen MemTable 序列化
       └── 多 TaskManager 可同时读取
```

### 2.3 FileSystem Router

```rust
/// FileSystem 路由器：SST → 远端, 非 SST → 本地
pub struct ForStRsFileSystemRouter {
    /// 远端 FileSystem (S3/HDFS) — SST 文件写入目标
    primary_fs: Box<dyn FileSystem>,
    /// 本地 FileSystem — WAL, MANIFEST 等元数据
    local_fs: LocalFs,
    /// SSD 文件缓存层（可选）
    file_cache: Option<FileBasedCache>,
}

impl FileSystem for ForStRsFileSystemRouter {
    fn create_writable_file(&self, path: &Path) -> Result<Box<dyn WritableFile>> {
        if Self::is_sst_file(path) {
            // SST → 远端 FS + 同时写入本地缓存 (write-through)
            self.primary_fs.create_writable_file(path)
        } else {
            // WAL/MANIFEST → 本地 FS
            self.local_fs.create_writable_file(path)
        }
    }

    fn open_random_access_file(&self, path: &Path) -> Result<Box<dyn RandomAccessFile>> {
        if Self::is_sst_file(path) {
            // SST 读取: 本地缓存优先 → 缓存未命中 → 远端拉取
            if let Some(cache) = &self.file_cache {
                cache.open_or_fetch(path, &*self.primary_fs)
            } else {
                self.primary_fs.open_random_access_file(path)
            }
        } else {
            self.local_fs.open_random_access_file(path)
        }
    }
}
```

### 2.4 FileOwnership 三级模型

```rust

pub enum FileOwnership {
    /// WAL, MANIFEST — 生命周期完全由 DB 管理
    PrivateOwnedByDb = 0,
    /// 新创建的 SST — DB 拥有，可在 Checkpoint 时转移给 JobManager
    ShareableOwnedByDb = 1,
    /// Restore 的 SST — 生命周期由 JobManager 管理
    NotOwned = 2,
}
```

### 2.5 Checkpoint 零拷贝

**创建 Checkpoint**：
```
1. Freeze MemTable (<1us, ArcSwap pointer swap)
2. 序列化 VersionSet → blob (SST 文件远端路径列表 + 元数据)
3. Frozen MemTable → Arrow IPC → 写入远端 Checkpoint 存储
4. SST 文件已在远端 → ownership 从 ShareableOwnedByDb → NotOwned (零字节拷贝)
5. 返回 blob 给 Flink Checkpoint Coordinator
```

**Restore 流程（无状态快速恢复）**：
```
1. 从远端 Checkpoint 存储下载 blob (<1MB 元数据)
2. 反序列化 VersionSet — 获取远端 SST 文件路径列表 (<10ms)
3. SST 文件已在远端 S3, 直接可读 (无需下载到本地)
4. 恢复 Frozen MemTable 数据 (从远端 blob, 通常 <100MB)
5. 本地 BlockCache/SSD Cache 冷启动, 随 Lookup 请求逐步预热
→ 作业恢复时间由 blob 下载 + 反序列化决定, 与维表数据量无关
```

**Rescaling 流程（无状态迁移）**：
```
1. 新 TaskManager 从远端 blob 恢复 VersionSet (<10ms)
2. SST 在远端 S3 共享, 新旧 TM 均可直接读取 (零数据迁移)
3. 按 KeyGroup range 裁剪 (clip_key_group_range)
4. 后台 Compaction 逐步清理不属于自己 range 的远端 SST
→ Rescaling 无需等待本地状态迁移, 立即可服务 Lookup
```

### 3.2 Java 组件设计

#### 3.2.1 ForStRsDeltaJoinSource（数据摄入算子）

接收上游 changelog 数据，将数据持续写入嵌入式 ForSt-RS。数据来源是通用的 Flink DataStream 管道——可以是 Kafka Source、数据库 CDC Source 或任意 Flink Source/Transform 算子的输出。

```java
/**
 * 数据摄入算子：接收上游 changelog 数据，写入本地 ForSt-RS。
 * 作为 DeltaJoin 的维表物化源。ForSt-RS 自主管理摄入、存储、服务全生命周期。
 * 数据来源为通用 Flink DataStream 管道，不绑定特定外部系统。
 */
public class ForStRsDeltaJoinSource extends AbstractStreamOperator<Void>
        implements OneInputStreamOperator<RowData, Void> {

    // ForSt-RS 引擎实例（嵌入式）
    private transient ForStRsBridge bridge;

    @Override
    public void processElement(StreamRecord<RowData> element) {
        // 上游 changelog → ForSt-RS put/delete
        RowData row = element.getValue();
        RowKind kind = row.getRowKind();
        byte[] key = keySerializer.serialize(row);
        byte[] value = valueSerializer.serialize(row);

        switch (kind) {
            case INSERT:
            case UPDATE_AFTER:
                bridge.put(key, value);
                break;
            case DELETE:
            case UPDATE_BEFORE:
                bridge.delete(key);
                break;
        }
    }

    @Override
    public void snapshotState(StateSnapshotContext context) {
        // ForSt-RS checkpoint 由 StateBackend 统一管理
        // SST 已在 S3, 零拷贝 ownership 转移
    }
}
```

**设计要点**：
- 数据来源于 Flink DataStream 管道（任意上游 Source/Transform 算子输出的 changelog）
- 不绑定特定外部系统，支持 Kafka、CDC、自定义 Source 等任意 changelog 来源
- 通过 `ForStRsBridge`（FFM/C ABI）与嵌入式 ForSt-RS 通信
- ForSt-RS 自主管理数据写入、Flush、Compaction 的全生命周期
- 支持 RowKind 四种操作：INSERT、UPDATE_BEFORE、UPDATE_AFTER、DELETE
- WriteBatch 批量写入，摊薄 FFM/C ABI 调用开销
- Checkpoint 时 SST 已在 S3，仅需 ownership 转移

#### 3.2.2 ForStRsLocalLookupFunction（本地 prefix_scan）

替代传统远程 RPC Lookup，直接读本地嵌入式 ForSt-RS，实现零网络延迟查询。

```java
/**
 * 本地 Lookup 函数，直接读取嵌入式 ForSt-RS。
 * 零 RPC — 通过 FFM/C ABI 调用 Rust prefix_scan。
 */
public class ForStRsLocalLookupFunction extends AsyncLookupFunction {

    private transient ForStRsBridge bridge;
    private transient LookupNormalizer lookupNormalizer;

    @Override
    public CompletableFuture<Collection<RowData>> asyncLookup(RowData keyRow) {
        RowData normalizedKey = lookupNormalizer.normalizeLookupKey(keyRow);
        byte[] keyBytes = keySerializer.serialize(normalizedKey);

        // 本地 prefix_scan — 零 RPC
        // ForSt-RS 通过 FFM/C ABI 直接调用 Rust prefix_scan
        return CompletableFuture.supplyAsync(() -> {
            List<byte[]> results = bridge.prefixScan(keyBytes);
            return results.stream()
                    .map(valueDeserializer::deserialize)
                    .collect(Collectors.toList());
        }, lookupExecutor);
    }
}
```

**设计要点**：
- 实现 Flink `AsyncLookupFunction` 接口，对 DeltaJoin Operator 透明
- 通过 `ForStRsBridge.prefixScan()` 调用本地 ForSt-RS 前缀扫描
- 返回 Arrow RecordBatch 零拷贝结果
- 使用独立 `lookupExecutor` 线程池避免阻塞 Flink 主线程
- 分层查询路径：MemTable → L1 BlockCache → L2 SSD Cache → L3 S3

### 3.3 数据一致性

DeltaJoin 采用**最终一致性模型**：
- 维表数据通过 changelog 持续写入 ForSt-RS，存在毫秒到秒级的物化延迟
- 事实表记录到达 DeltaJoin Operator 时，查询到的维表状态可能略滞后
- 这与传统远程 Lookup Join 的一致性语义一致——查询时点的维表快照
- 通过监控维表物化延迟（摄入算子的 watermark 差值）可观测数据新鲜度

### 3.4 性能对比：本地 Lookup vs 远程 RPC

| 路径 | 本地 ForSt-RS | 远程 RPC Lookup |
|------|--------------|-----------------|
| L1 BlockCache hit | < 10us | N/A |
| L2 SSD Cache hit | 10-100us | N/A |
| L3 S3 cold fetch | 1-50ms | N/A |
| 网络往返 (同机房) | 无 | 0.5-2ms |
| 网络往返 (跨机房) | 无 | 5-20ms |
| Batch 10 keys | < 50us (本地) | 2-10ms (远程) |
| P99 延迟 (热数据) | < 100us | 5-50ms |

## 4. Multi DeltaJoin（长期）

### 4.1 问题描述

`A join B join C` 场景：事实表与多张维表的关联查询。传统方案下，每张维表需要独立的 ForSt-RS 实例进行物化和 Lookup，产生以下问题：
- **资源浪费**：N 张维表需要 N 个 ForSt-RS 实例，各自占用 MemTable + BlockCache
- **多次 Lookup**：DeltaJoin Operator 对每张维表分别 prefix_scan，延迟累加
- **Recovery 慢**：Rescaling 时需要恢复 N 个独立的状态实例

### 4.2 架构设计

```
┌───────────────────────────────────────────────────────────────────────────┐
│                                                                            │
│  数据摄入层 (每张维表独立消费 changelog)                                   │
│                                                                            │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐                     │
│  │ changelog(B) │  │ changelog(C) │  │ changelog(D) │                     │
│  │  (Kafka/CDC) │  │  (Kafka/CDC) │  │  (Kafka/CDC) │                     │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘                     │
│         │                  │                  │                              │
│         ▼                  ▼                  ▼                              │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐                     │
│  │ ForSt-RS (B) │  │ ForSt-RS (C) │  │ ForSt-RS (D) │                     │
│  │  MemTable    │  │  MemTable    │  │  MemTable    │                     │
│  │  → Flush     │  │  → Flush     │  │  → Flush     │                     │
│  │  → SST on S3 │  │  → SST on S3 │  │  → SST on S3 │                     │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘                     │
│         │                  │                  │                              │
│         └────────────┬─────┴──────────────────┘                              │
│                      ▼                                                       │
│  ┌──────────────────────────────────────────────┐                           │
│  │  Remote Merge Service (独立服务)              │                           │
│  │                                               │                           │
│  │  输入: SST(B) + SST(C) + SST(D) on S3        │                           │
│  │  处理: composite key 编码, 合并为 unified SST │                           │
│  │  输出: merged SST set on S3                   │                           │
│  │  + Server-side Compaction                     │                           │
│  └──────────────────┬───────────────────────────┘                           │
│                      ▼                                                       │
│  ┌─────────────────────────────────────────────────────────────────────┐    │
│  │  Flink TaskManager                                                   │    │
│  │                                                                      │    │
│  │  ForSt-RS (Merged View)                                              │    │
│  │    读取 merged SST set                                               │    │
│  │    单次 prefix_scan(join_key)                                        │    │
│  │    → 返回 B ⋈ C ⋈ D 的全部匹配结果                                 │    │
│  │                                                                      │    │
│  │  DeltaJoin Operator                                                  │    │
│  │    事实表 A → ForStRsLocalLookupFunction.asyncLookup(key)            │    │
│  │    → 单次 prefix_scan → Arrow RecordBatch (多表联合结果)             │    │
│  │    → JoinedRowData 拼装 → Sink                                       │    │
│  └─────────────────────────────────────────────────────────────────────┘    │
│                                                                            │
└───────────────────────────────────────────────────────────────────────────┘
```

### 4.3 数据流

```
维表 B changelog → Flink DataStream → ForSt-RS instance B → SST(B) on S3
维表 C changelog → Flink DataStream → ForSt-RS instance C → SST(C) on S3
维表 D changelog → Flink DataStream → ForSt-RS instance D → SST(D) on S3

Remote Merge Service:
  输入: SST(B), SST(C), SST(D) on S3
  处理: composite key 编码, 将多表列合并为统一 SST
  输出: merged SST set on S3

TaskManager 内 ForSt-RS (Merged View):
  读取 merged SST set
  单次 prefix_scan(join_key) → 返回 A ⋈ B ⋈ C ⋈ D 全部结果
```

### 4.4 Composite Key 设计

Multi DeltaJoin 合并多张维表的数据到统一 SST 集合，需要通过 composite key 区分不同维表的数据：

```
composite_key = [join_key_bytes][dimension_table_id (u16)][value_columns_bytes]
```

- **join_key_bytes**：所有维表共享的 join key 前缀，确保 prefix_scan 能一次扫描所有相关数据
- **dimension_table_id**：2 字节维表标识符，区分数据来源
- **value_columns_bytes**：该维表的列值

**prefix_scan 行为**：以 `join_key_bytes` 为前缀扫描，返回所有匹配维表的数据，由 Lookup Function 按 `dimension_table_id` 拆分并组装多表 Join 结果。

### 4.5 Multi DeltaJoin 优势

| 维度 | 传统多实例 Lookup | Multi DeltaJoin |
|------|------------------|-----------------|
| Lookup 次数 | N 张维表 = N 次 prefix_scan | **1 次 prefix_scan** |
| 延迟 | N * 单次延迟 | 单次延迟 |
| 状态存储 | N 个独立 ForSt-RS 实例的 MemTable + BlockCache | 统一 Merged View，共享 BlockCache |
| 缓存效率 | 每张表独立 BlockCache | 统一 SST 共享 BlockCache |
| 数据局部性 | 同一 key 分散在多个 SST | 同一 key 的多表数据物理相邻 |
| Recovery 速度 | N 个实例分别恢复 blob (<10ms each) | 单个 Merged View 恢复 blob (<10ms) |

## 5. Remote Merge Service

### 5.1 职责定位

Remote Merge Service 是独立于 Flink TaskManager 的专用服务进程，承担两项核心职责：

1. **SST 合并**（Multi DeltaJoin）：将多张维表各自产出的 SST 文件合并为统一的 SST 集合
2. **Server-side Compaction**：接管 ForSt-RS 的 Compaction 工作负载，将 CPU 密集操作从 TaskManager 卸载

### 5.2 SST 合并流程

```
┌──────────────────────────────────────┐
│  Remote Merge Service                 │
│                                       │
│  1. 监听各维表 SST 输出 (S3 路径)    │
│  2. 从 S3 读取输入 SST               │
│  3. Composite key 编码               │
│     [join_key][table_id][value]       │
│  4. 按 join_key 前缀对齐, 合并 SST   │
│  5. 输出 merged SST 直写 S3          │
│  6. 通知 TaskManager 更新 VersionSet  │
└──────────────────────────────────────┘
```

**合并策略**：
- **Composite Key 编码**：所有维表的数据按 `[join_key][table_id][value]` 统一编码
- **前缀对齐**：确保同一 join_key 下所有维表的数据物理相邻
- **增量合并**：仅处理增量变更的 SST，避免全量重建
- **版本管理**：维护合并元数据（版本号、输入输出 SST 映射关系）

### 5.3 Server-side Compaction

Compaction 是 LSM-Tree 的核心开销。在 Single DeltaJoin 中，Compaction 默认运行在 TaskManager 内部。当 TM 资源紧张时，可将 Compaction 工作负载卸载到 Remote Merge Service。

```
┌──────────────────────────────────────┐
│  Flink TaskManager (精简模式)         │
│                                       │
│  ForSt-RS Engine                      │
│    ├── MemTable 写入                  │
│    ├── Flush → SST 直写 S3           │
│    ├── prefix_scan 读取               │
│    └── Compaction → 委托远程服务      │
└───────────────┬──────────────────────┘
                │  Compaction 请求
                ▼
┌──────────────────────────────────────┐
│  Remote Merge Service                 │
│                                       │
│  接收 Compaction 请求                 │
│  从 S3 读取输入 SST                   │
│  执行 Compaction (合并 + 压缩)        │
│  输出 SST 直写 S3                     │
│  返回 Compaction 结果元数据           │
└──────────────────────────────────────┘
```

**TM 资源卸载效果**：

| 工作负载 | 卸载前 (TM 内) | 卸载后 (远程服务) |
|---------|---------------|-----------------|
| MemTable 写入 | TM 内 | TM 内 (保留) |
| Flush → S3 | TM 内 | TM 内 (保留) |
| prefix_scan 读取 | TM 内 | TM 内 (保留) |
| Compaction | **TM 内执行** | **远程服务执行** |
| CPU 峰值 | 高 (Compaction 密集) | 低 (仅写入 + 读取) |

### 5.4 基础设施共享

SST 合并与 Server-side Compaction 共享相同的基础设施：
- 相同的 S3 访问层
- 相同的 SST 读写能力
- 统一的服务部署和运维
- Merge 可视为 Compaction 的扩展能力（多表 SST 合并 = 跨表 Compaction）

### 5.5 Java 协调组件

```java
/**
 * Multi DeltaJoin 合并协调器。
 * 监控各维表 ForSt-RS 实例的 SST 输出，
 * 触发 Remote Merge Service 进行 SST 合并。
 */
public class ForStRsMultiJoinMergeCoordinator {

    private final List<ForStRsBridge> dimensionTableBridges;
    private final RemoteMergeServiceClient mergeClient;
    private final ForStRsBridge mergedViewBridge;

    /**
     * 当任一维表产出新 SST 后触发合并。
     */
    public void onSstFlushed(String tableId, List<String> newSstPaths) {
        // 收集所有维表最新 SST 集合
        Map<String, List<String>> allSsts = collectLatestSsts();

        // 提交合并请求到 Remote Merge Service
        MergeRequest request = MergeRequest.builder()
                .joinKey(joinKeyPrefix)
                .inputSsts(allSsts)
                .outputPath(mergedSstPath)
                .build();

        mergeClient.submitMerge(request)
                .thenAccept(result -> {
                    // 更新 Merged View 的 VersionSet
                    mergedViewBridge.installMergedSsts(result.outputSstPaths());
                });
    }
}
```

## 6. 性能预估

### 6.1 Single DeltaJoin Lookup 延迟

| 路径 | 延迟 |
|------|------|
| L1 BlockCache hit (内存) | < 10us |
| L2 SSD Cache hit (NVMe) | 10-100us |
| L3 S3 cold fetch | 1-50ms |
| Batch 10 keys (本地) | < 50us |

**热数据场景（>80% cache hit rate）**：延迟在微秒级别。

### 6.2 Multi DeltaJoin 延迟

| 场景 | 传统 N 次 Lookup | Multi DeltaJoin (1 次) |
|------|------------------|------------------------|
| 3 张维表, L1 hit | < 30us (3x10us) | < 15us (1 次扫描, 数据相邻) |
| 3 张维表, L2 hit | 30-300us | 10-120us |
| 3 张维表, cold | 3-150ms | 1-60ms |

### 6.3 资源开销

| 资源 | Single DeltaJoin | Multi DeltaJoin |
|------|-----------------|-----------------|
| TM 内存 | MemTable + BlockCache (256MB-4GB) | 多实例 MemTable + 统一 BlockCache |
| TM 磁盘 | SSD Cache (可选, 10-100GB) | SSD Cache (可选) |
| 网络 | 数据摄入 + S3 读取 | 数据摄入 + S3 读取 + Merge Service 通信 |
| 远端存储 | SST 文件 (与维表数据量成正比) | SST (各维表) + Merged SST |
| 远端计算 | 无 (或 Remote Compaction) | Remote Merge Service + Remote Compaction |

### 6.4 适用场景

| 场景 | 推荐方案 |
|------|---------|
| 单维表 Join, 热数据为主 | **Single DeltaJoin** — cache hit 率高, 微秒级延迟 |
| 多维表 Join (A join B join C) | **Multi DeltaJoin** — 单次 prefix_scan 返回全部结果 |
| TM 资源受限 (CPU 紧张) | 启用 **Server-side Compaction** — 卸载 Compaction 负载 |
| 超大维表 (>100GB), 低频 Lookup | 评估是否值得本地物化 |
| 延迟敏感 (P99 < 1ms) | **Single/Multi DeltaJoin** — 避免网络延迟 |

## 7. 风险与缓解

### 7.1 Single DeltaJoin 风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| S3 写入延迟影响 Flush | 高 | 中 | 异步 Flush + 背压控制; MemTable 大小可配置 |
| TM 资源压力 | 中 | 高 | 本地无状态，仅 Cache; SST 全量在远端; Cache 大小可配置; 可卸载 Compaction |
| S3 网络抖动导致 Lookup 长尾 | 中 | 中 | L2 SSD Cache 吸收大部分 S3 读取; Prefetch 预取 |
| Rescaling 时 SST 数据裁剪 | 中 | 中 | 后台 Compaction 逐步清理无关数据 |
| 数据摄入延迟导致结果陈旧 | 低 | 低 | DeltaJoin 本身是最终一致性; 可监控延迟指标 |

### 7.2 Multi DeltaJoin 风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Merge Service 单点故障 | 中 | 高 | 多副本部署; 降级回多次 Lookup 模式 |
| 合并延迟导致结果陈旧 | 中 | 中 | 增量合并减少延迟; 可配置合并频率 |
| 多表 Schema 演化不同步 | 中 | 中 | 合并时检查 Schema 版本一致性 |
| Merged SST 存储膨胀 | 低 | 中 | 定期清理过期 Merged SST; 共享 Compaction 服务 |

### 7.3 Server-side Compaction 风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 远程服务延迟导致 Compaction 积压 | 中 | 高 | 可回退到 TM 内 Compaction; 队列监控告警 |
| 网络传输增加 Compaction 延迟 | 高 | 低 | SST 已在 S3, 远程服务直接读写; 无额外传输 |
| 服务运维复杂度 | 中 | 中 | 与 Merge Service 共享基础设施; 统一运维 |
