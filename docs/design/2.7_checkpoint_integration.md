## 1. 设计目标与约束

### 1.1 设计目标

Checkpoint 是 Flink 有状态计算的核心容错机制。ForSt-RS 的 Checkpoint 集成需要在模式 B（纯内存 VersionSet）下实现与 Flink Checkpoint Coordinator 的完整对接。核心目标：

1. **消除同步阶段 flush 阻塞**：ForSt 当前 `getLiveFiles(true)` 强制 flush MemTable 阻塞前台写入（文档 1.7 瓶颈 B5），ForSt-RS 应支持可选的非强制 flush，仅冻结 MemTable 而不等待 flush 完成
2. **纯内存 VersionSet 快照**：无 MANIFEST 文件（模式 B，文档 1.16），Checkpoint 同步阶段原子获取 VersionSet 快照并序列化为 blob
3. **增量 SST 差分追踪**：兼容 Flink 的 PreviousSnapshot 机制（文档 1.5 §3.2），只上传新增 SST 文件
4. **Rescaling 兼容**：支持 KeyGroup 范围裁剪（文档 1.13 §3.4 clipDBWithKeyGroupRange）
5. **Compaction 协同**：Checkpoint 期间禁止 Compaction 删除 SST 文件，但不阻塞 Compaction 执行（文档 2.6）

### 1.2 已知约束

| 约束 ID | 来源 | 内容 |
|---------|------|------|
| C1 | 文档 1.16 | 元数据采用模式 B（纯 Checkpoint），VersionSet 仅内存管理 |
| C2 | 文档 1.16 §5.1 | Flush/Compaction 版本更新为纯内存操作，无 fsync |
| C5 | 文档 1.4 | 最小桥接接口集：5 个 Checkpoint 操作 |
| C6 | 设计规范 | P0 优先级包含 R10（Checkpoint 集成） |
| C10 | 文档 1.7 | B5: Checkpoint 同步阶段 flush 阻塞 |

### 1.3 与当前 ForSt 的差异

| 维度 | ForSt (当前) | ForSt-RS (目标) | 改进点 |
|------|-------------|-----------------|--------|
| **元数据源** | MANIFEST 文件（本地 + 上传到 CP Storage） | 纯内存 VersionSet → 序列化 blob | 消除 MANIFEST fsync，简化恢复路径 |
| **同步阶段** | `disableFileDeletions()` + `getLiveFiles(true)` 强制 flush | 原子 VersionSet 快照 + 可选 freeze MemTable（不等 flush） | 消除 B5 flush 阻塞 |
| **文件追踪** | 基于 MANIFEST 解析的活跃文件列表 | VersionSet.live_sst_files() 直接返回 | 无需解析 MANIFEST |
| **增量 diff** | Java 侧 PreviousSnapshot 差分 | Java 侧逻辑不变，Rust 侧提供文件列表 | 保持兼容 |
| **恢复路径** | 下载 MANIFEST + SST → 打开 DB | 下载 blob + SST → 反序列化 VersionSet → 构建引擎 | 恢复 <10ms（文档 1.16） |
| **Rescaling** | `clipDBWithKeyGroupRange()` → deleteFilesInRanges + deleteRange | 类似机制，但在 Rust 侧执行 | 消除 JNI 开销 |

## 2. 方案设计

### 2.1 Checkpoint 生命周期映射

ForSt-RS 的 Checkpoint 集成需要对齐 Flink 的四阶段 Checkpoint 生命周期（文档 1.5 §3.1）：

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Flink Checkpoint 生命周期                        │
├─────────┬────────────────────────┬──────────────────────────────────┤
│  阶段    │  Flink 侧 (Java)       │  ForSt-RS 侧 (Rust via C ABI)  │
├─────────┼────────────────────────┼──────────────────────────────────┤
│ 触发     │ Barrier 到达           │ (无操作)                         │
│ 同步     │ syncPrepareResources() │ prepare_checkpoint()            │
│         │                        │   → freeze MemTable             │
│         │                        │   → VersionSet.snapshot()        │
│         │                        │   → serialize_to_blob()          │
│         │                        │   → live_sst_files()             │
│         │                        │ disable_file_deletions()        │
│ 异步     │ asyncSnapshot()        │ (无 Rust 操作，Java 侧上传文件)   │
│         │ 上传新增 SST → CP Store │                                  │
│         │ 上传 metadata blob      │                                  │
│         │ enable_file_deletions() │ enable_file_deletions()         │
│ 完成     │ notifyCheckpointComplete│ (无操作)                         │
│         │ 清理 uploadedSstFiles   │                                  │
└─────────┴────────────────────────┴──────────────────────────────────┘
```

### 2.2 同步阶段（Sync Phase）设计

同步阶段是 Checkpoint 的关键路径，在 Task 线程中执行，必须尽可能快。

#### 2.2.1 ForSt-RS 同步操作序列

```rust
/// Checkpoint 同步阶段入口
/// 在 Flink Task 线程中通过 C ABI 调用
pub fn prepare_checkpoint(&self) -> Result<CheckpointSnapshot> {
    // Step 1: 原子获取 VersionSet 快照
    // 使用 Arc<Version> 引用计数，无需加锁拷贝
    let version_snapshot = self.version_set.snapshot();

    // Step 2: 冻结当前活跃 MemTable
    // 将 Mutable MemTable 转为 Immutable（追加到 imm_list）
    // 这是原子操作：swap active memtable pointer
    // 注意：不等待 flush 完成（解决 B5）
    self.freeze_active_memtable()?;

    // Step 3: 序列化 VersionSet 为 blob
    // 包含：所有 CF 的 Level 布局 + SST 文件列表 + next_file_number + last_sequence
    let metadata_blob = version_snapshot.serialize_to_blob()?;

    // Step 4: 收集活跃 SST 文件列表
    // Java 侧用于增量 diff 追踪（PreviousSnapshot 机制）
    let live_files = version_snapshot.live_sst_files();

    Ok(CheckpointSnapshot {
        metadata_blob,
        live_sst_files: live_files,
    })
}
```

#### 2.2.2 MemTable 冻结策略

与 ForSt 的 `getLiveFiles(true)` 强制 flush 不同，ForSt-RS 采用**冻结但不等待 flush**的策略：

```
ForSt (当前):
  getLiveFiles(flush=true)
    → flush MemTable to SST (同步等待 IO 完成)
    → 阻塞时间 = MemTable 大小 / 磁盘写入速度
    → 64MB MemTable + 500MB/s SSD ≈ 128ms 阻塞

ForSt-RS (目标):
  freeze_active_memtable()
    → swap MemTable pointer (原子操作，<1us)
    → 后台 flush 线程异步写入 SST
    → 冻结的 ImmutableMemTable 在快照中记录
    → 不等待 flush 完成
```

**冻结 MemTable 的 Checkpoint 一致性保证**：

同步阶段冻结的 MemTable 数据需要包含在 Checkpoint 中。有两种处理策略：

| 策略 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A: 等待异步 flush 完成 | 异步阶段等待所有 ImmutableMemTable flush 为 SST，然后上传 | 简单，与现有 Flink 流程一致 | 异步阶段可能等待 flush |
| **B: 序列化 MemTable 到 blob（选定）** | 未 flush 的 ImmutableMemTable 数据也序列化到 metadata blob | Checkpoint 不依赖 flush 时机 | blob 可能较大 |

**选定方案 B 的理由**：
- 避免异步阶段对 flush 时机的依赖，使 Checkpoint 完全确定性
- MemTable 典型大小 64MB，序列化后通过压缩可降至 10-30MB
- 恢复时直接从 blob 重建 MemTable，无需额外的 SST 下载

**方案 B 的 blob 结构**：

```
CheckpointBlob 结构:
┌─────────────────────────────────────────────┐
│ Header (16 bytes)                           │
│   magic: "FRCP" (4B)                        │
│   version: u16                              │
│   flags: u16                                │
│   blob_size: u64                            │
├─────────────────────────────────────────────┤
│ VersionSet Snapshot                         │
│   num_column_families: u32                  │
│   for each CF:                              │
│     cf_id: u32                              │
│     cf_name: LenPrefixedString              │
│     num_levels: u32                         │
│     for each level:                         │
│       level_id: u32                         │
│       num_files: u32                        │
│       for each file:                        │
│         file_number: u64                    │
│         file_size: u64                      │
│         smallest_key: LenPrefixedBytes      │
│         largest_key: LenPrefixedBytes       │
│         min_sequence: u64                   │
│         max_sequence: u64                   │
│         num_entries: u64                    │
│   next_file_number: u64                     │
│   last_sequence: u64                        │
├─────────────────────────────────────────────┤
│ Frozen MemTable Data (optional)             │
│   num_frozen_memtables: u32                 │
│   for each frozen memtable:                 │
│     cf_id: u32                              │
│     num_entries: u64                        │
│     data: CompressedArrowIPC               │
│       (Arrow IPC format + LZ4 compression)  │
├─────────────────────────────────────────────┤
│ Footer                                      │
│   checksum: CRC32 (4B)                      │
│   blob_length: u64                          │
│   magic: "FRCP" (4B)                        │
└─────────────────────────────────────────────┘
```

### 2.3 异步阶段（Async Phase）设计

异步阶段在 Flink 的 asyncSnapshotCallable 线程中执行。ForSt-RS 的异步阶段主要工作在 Java 侧完成，Rust 引擎仅提供文件列表。

#### 2.3.1 Java 侧异步操作流程

```
asyncSnapshot():
  1. 从 CheckpointSnapshot 获取 live_sst_files 列表
  2. 增量 diff（复用 Flink PreviousSnapshot 机制）:
     for each sst_file in live_sst_files:
       if sst_file in previousSnapshot.confirmedSstFiles:
         → PlaceholderStreamStateHandle（零拷贝引用）
       else:
         → 加入 toTransferFiles（需上传）
  3. 上传新增 SST 文件到 Checkpoint Storage
  4. 上传 metadata_blob 作为 miscFiles 的一部分
  5. 构建 ForStRsIncrementalKeyedStateHandle:
     - sstFiles: 所有 SST handle（shared scope）
     - metadataBlob: blob handle
     - metaStateHandle: state meta info handle
  6. 调用 enable_file_deletions() 解除 Compaction 文件删除限制
```

#### 2.3.2 增量 diff 追踪

ForSt-RS 的增量 diff 追踪与当前 ForSt 的 PreviousSnapshot 机制兼容，差异在于：

| 维度 | ForSt (当前) | ForSt-RS (目标) |
|------|-------------|-----------------|
| **文件列表来源** | `getLiveFiles()` 解析 MANIFEST | `CheckpointSnapshot.live_sst_files` 直接从内存 VersionSet |
| **文件标识** | 文件名（如 "000042.sst"） | file_number（u64），Java 侧转为文件名 |
| **MANIFEST 上传** | 作为 miscFiles 上传 | 不上传 MANIFEST（不存在），改为上传 metadata_blob |
| **CURRENT 文件** | 异步阶段重写 | 不需要（无 MANIFEST 则无 CURRENT） |
| **PreviousSnapshot** | Java 侧维护，与 Rust 引擎无关 | 同上，Java 侧逻辑完全复用 |

#### 2.3.3 文件删除保护（disableFileDeletions）

Checkpoint 期间需要保护 SST 文件不被 Compaction 删除。ForSt-RS 使用引用计数机制：

```rust
/// 文件删除保护器
pub struct FileDeletionGuard {
    /// 引用计数：每次 disable_file_deletions 加 1，enable 减 1
    /// 当计数 > 0 时，Compaction 不删除已废弃的 SST 文件
    disable_count: AtomicU32,
    /// 待删除文件队列（Compaction 期间产生的废弃文件暂存）
    pending_deletions: Mutex<Vec<u64>>,  // file_numbers
}

impl FileDeletionGuard {
    pub fn disable(&self) {
        self.disable_count.fetch_add(1, Ordering::SeqCst);
    }

    pub fn enable(&self) {
        let prev = self.disable_count.fetch_sub(1, Ordering::SeqCst);
        if prev == 1 {
            // 计数归零，执行积压的文件删除
            self.flush_pending_deletions();
        }
    }

    /// Compaction 完成后尝试删除废弃文件
    pub fn try_delete_file(&self, file_number: u64) -> bool {
        if self.disable_count.load(Ordering::SeqCst) > 0 {
            self.pending_deletions.lock().push(file_number);
            false  // 暂不删除
        } else {
            true  // 可以删除
        }
    }
}
```

### 2.4 恢复路径（Restore Path）设计

#### 2.4.1 恢复操作分类

与 ForSt 对齐（文档 1.5 §3.4），ForSt-RS 支持三种恢复场景：

| 场景 | ForSt 操作类 | ForSt-RS 等价操作 |
|------|-------------|------------------|
| 全新启动 | `ForStNoneRestoreOperation` | `Engine::open(opts)` 创建空引擎 |
| 增量恢复 | `ForStIncrementalRestoreOperation` | `Engine::restore(blob, sst_dir, opts)` |
| 全量恢复 | `ForStHeapTimersFullRestoreOperation` | `Engine::restore(blob, sst_dir, opts)` + 数据导入 |

#### 2.4.2 增量恢复流程

```
ForSt-RS 增量恢复:

  1. Java 侧：从 Checkpoint Storage 下载文件到本地临时目录
     - 下载所有 SST 文件（4 线程并行，复用 ForStStateDataTransfer）
     - 下载 metadata_blob

  2. Java 侧：通过 C ABI 调用 Rust 恢复
     engine_handle = forst_rs_restore(
       blob_ptr, blob_len,        // metadata_blob 字节
       sst_dir_ptr, sst_dir_len,  // SST 文件所在目录
       opts_handle                // 引擎配置
     )

  3. Rust 侧：Engine::restore()
     a) 反序列化 metadata_blob:
        - 解析 Header，验证 magic "FRCP" 和 version
        - 重建 VersionSet：遍历 CF → Level → File 列表
        - 重建未 flush 的 MemTable（如果 blob 包含冻结 MemTable 数据）

     b) 验证 SST 文件完整性:
        - 对比 VersionSet 中的文件列表与 sst_dir 中的实际文件
        - 缺失文件 → 返回错误
        - 多余文件 → 忽略（可能是之前残留）

     c) 构建引擎实例:
        - 初始化 BlockCache（空缓存，后续按需填充）
        - 启动 Compaction 调度器
        - 打开 SST 文件句柄（延迟打开，首次读取时打开）

     d) 返回 Engine handle（Box<Engine> as i64）

  4. Java 侧：注册 ColumnFamilyHandle，恢复 State 元数据
```

恢复时间对比：

```
ForSt (当前):
  下载 MANIFEST → 解析 VersionEdit 序列 → 构建 Version → 打开所有 SST 文件
  恢复时间 = 下载时间 + MANIFEST 解析（O(编辑次数)）+ 文件打开

ForSt-RS (目标):
  下载 blob → 反序列化 VersionSet → 延迟打开 SST 文件
  恢复时间 = 下载时间 + blob 反序列化（O(文件数)）

  优势：blob 是最终状态的快照，不需要回放编辑历史
  典型 MANIFEST 可能有 10K+ VersionEdit，而 blob 直接是最终态
```

#### 2.4.3 Rescaling 支持

当并行度变更时，subtask 的 KeyGroup 范围可能变化。ForSt-RS 需要实现 KeyGroup 范围裁剪：

```rust
/// KeyGroup 范围裁剪
/// 等价于 ForStIncrementalCheckpointUtils.clipDBWithKeyGroupRange()
pub fn clip_key_group_range(
    &self,
    target_range: KeyGroupRange,
    current_range: KeyGroupRange,
) -> Result<()> {
    // Step 1: 计算需要删除的 KeyGroup 范围
    // current_range = [0, 63]，target_range = [0, 31]
    // → 需删除 [32, 63] 对应的 key 范围

    let ranges_to_delete = compute_ranges_to_delete(
        current_range, target_range
    );

    for range in ranges_to_delete {
        // Step 2: 快速文件级删除
        // 对完全落入删除范围的 SST 文件，直接标记删除（O(1)）
        self.delete_files_in_range(&range.start_key, &range.end_key)?;

        // Step 3: 范围删除墓碑
        // 对部分重叠的 SST 文件，放置 DeleteRange 墓碑
        // 后续 Compaction 时物理清理
        self.delete_range(&range.start_key, &range.end_key)?;
    }

    // Step 4: 可选的 CompactRange
    // 立即清理墓碑覆盖的区域（可延迟到正常 Compaction）
    // self.compact_range(&target_start_key, &target_end_key)?;

    Ok(())
}

/// 计算 KeyGroup 前缀字节范围
fn compute_ranges_to_delete(
    current: KeyGroupRange,
    target: KeyGroupRange,
) -> Vec<KeyRange> {
    let mut ranges = Vec::new();

    // 删除 current.start .. target.start 范围
    if current.start < target.start {
        ranges.push(KeyRange {
            start_key: key_group_prefix(current.start),
            end_key: key_group_prefix(target.start),
        });
    }

    // 删除 target.end+1 .. current.end+1 范围
    if target.end < current.end {
        ranges.push(KeyRange {
            start_key: key_group_prefix(target.end + 1),
            end_key: key_group_prefix(current.end + 1),
        });
    }

    ranges
}
```

**KeyGroup 前缀编码**：

ForSt-RS 必须兼容 Flink 的 KeyGroup 前缀编码格式（文档 1.13 §3.2 CompositeKeySerializationUtils）：

```
Key 编码格式:
┌──────────────────┬────────────────────┬─────────────┐
│ KeyGroup Prefix  │ Key Bytes          │ Namespace   │
│ (1-2 bytes)      │ (variable)         │ (variable)  │
└──────────────────┴────────────────────┴─────────────┘

KeyGroup 前缀长度:
  maxParallelism <= 128  → 1 byte
  maxParallelism > 128   → 2 bytes (big-endian)

前缀计算:
  keyGroup = murmurHash(key.hashCode()) % maxParallelism
  prefix = keyGroup 按 big-endian 编码（1 或 2 字节）
```

### 2.5 多 Handle 恢复与 IngestDB

Scale-in（并行度减少）场景下，一个 subtask 可能需要恢复多个 State Handle 的数据。ForSt-RS 支持两种合并策略：

#### 2.5.1 IngestDB 模式（推荐）

```rust
/// 从多个外部 SST 目录导入数据
/// 等价于 RocksDB IngestDB / IngestExternalFile
pub fn ingest_external_files(&self, file_dirs: &[&Path]) -> Result<()> {
    for dir in file_dirs {
        // 枚举目录中的 SST 文件
        let sst_files: Vec<PathBuf> = self.fs.list(dir)?
            .iter()
            .filter(|f| f.extension() == Some("sst"))
            .collect();

        // 直接将外部 SST 文件链接/拷贝到引擎数据目录
        // 并注册到 VersionSet（作为 L0 文件）
        for sst_file in sst_files {
            let file_number = self.version_set.allocate_file_number();
            let dest = self.data_dir.join(format!("{:06}.sst", file_number));

            // 优先硬链接，失败则拷贝
            self.fs.link_or_copy(&sst_file, &dest)?;

            // 读取 SST 元数据
            let meta = SstReader::read_metadata(&dest)?;

            // 注册到 VersionSet (L0)
            self.version_set.apply(VersionEdit {
                new_files: vec![(0, SstFileMeta {
                    file_number,
                    file_size: meta.file_size,
                    smallest_key: meta.smallest_key.clone(),
                    largest_key: meta.largest_key.clone(),
                    min_sequence: meta.min_sequence,
                    max_sequence: meta.max_sequence,
                    num_entries: meta.num_entries,
                })],
                deleted_files: vec![],
                ..Default::default()
            })?;
        }
    }

    // 触发 Compaction 整理 L0 文件
    self.trigger_compaction();

    Ok(())
}
```

#### 2.5.2 恢复流程编排（Java 侧）

```
多 Handle 恢复（Scale-in）:

  1. findTheBestStateHandleForInitial():
     - 选择 KeyGroup 重叠最大的 handle 作为 base
     - 评分：交集 KeyGroup 数量优先，重叠比例其次

  2. 恢复 base handle:
     - 下载 SST + blob → forst_rs_restore()
     - clipKeyGroupRange() 裁剪到目标范围

  3. 恢复其他 handles:
     for each remaining handle:
       - 下载 SST 到临时目录
       - forst_rs_ingest_external_files(engine, temp_dir)
       - clipKeyGroupRange() 裁剪导入的数据

  4. 清理临时目录

  5. 恢复增量历史:
     - 如果 KeyGroup 范围未变化，恢复 backendUID + uploadedSstFiles
     - 否则重置增量历史（后续 Checkpoint 上传所有文件）
```

### 2.6 C ABI Checkpoint 接口

通过 Bridge 层（文档 2.5）暴露的 5 个 Checkpoint 相关 C ABI 函数：

```rust
/// 1. 准备 Checkpoint 快照（同步阶段调用）
/// 返回 CheckpointSnapshot handle
#[no_mangle]
pub extern "C" fn forst_rs_prepare_checkpoint(

/// 2. 获取序列化的 metadata blob

#[no_mangle]
pub extern "C" fn forst_rs_get_checkpoint_blob(

    blob_ptr: *mut *const u8, // 输出: blob 数据指针
    blob_len: *mut u64,       // 输出: blob 长度
) -> i32;

/// 3. 获取活跃 SST 文件列表
/// 返回 JSON 格式的文件列表（简化桥接）
```

### 2.7 与 Compaction 的协同

Checkpoint 与 Compaction 有两个交互点：

#### 2.7.1 文件删除保护

```
时序图:

Task Thread          Compaction Thread        FileDeletionGuard
    │                      │                        │
    │ disable_file_deletions()──────────────────────→│ count=1
    │                      │                        │
    │ prepare_checkpoint() │                        │
    │                      │ compaction_complete()   │
    │                      │ try_delete(file42) ────→│ count>0, 加入 pending
    │                      │                        │
    │ (异步上传 SST...)    │                        │
    │                      │                        │
    │ enable_file_deletions()──────────────────────→│ count=0
    │                      │                        │ flush_pending: 删除 file42
    │                      │                        │
```

#### 2.7.2 VersionSet 一致性

Compaction 和 Checkpoint 都会读取 VersionSet，需要保证一致性：

- **读取**：使用 `Arc<Version>` 引用计数，无锁读取当前版本
- **更新**：Compaction 通过 `version_set.apply(edit)` 原子替换 current Version
- **快照**：Checkpoint 通过 `version_set.snapshot()` 获取当前 Version 的 Arc 引用
- **并发安全**：快照持有 Arc 引用期间，即使 Compaction 更新了 current Version，快照仍然引用旧版本（不受影响）

```rust
/// VersionSet 并发访问模型
pub struct VersionSetImpl {
    /// 当前版本，使用 ArcSwap 实现无锁原子替换
    current: ArcSwap<Version>,

    /// 下一个可用文件号（原子递增）
    next_file_number: AtomicU64,

    /// 最新序列号（原子递增）
    last_sequence: AtomicU64,
}

impl VersionSet for VersionSetImpl {
    fn current(&self) -> Arc<Version> {
        self.current.load_full()
    }

    fn apply(&self, edit: VersionEdit) -> Result<Arc<Version>> {
        // 构建新版本（基于当前版本 + edit 增量）
        let old = self.current.load_full();
        let new_version = Arc::new(old.apply_edit(&edit)?);

        // 原子替换当前版本
        self.current.store(new_version.clone());

        // 更新全局序列号
        if let Some(seq) = edit.last_sequence {
            self.last_sequence.store(seq, Ordering::Release);
        }

        Ok(new_version)
    }

    fn snapshot(&self) -> VersionSetSnapshot {
        VersionSetSnapshot {
            version: self.current.load_full(),
            next_file_number: self.next_file_number.load(Ordering::Acquire),
            last_sequence: self.last_sequence.load(Ordering::Acquire),
        }
    }
}
```

### 3.1 新增 StateHandle 类型

ForSt-RS 需要一个新的 KeyedStateHandle 实现，替代 `IncrementalRemoteKeyedStateHandle`：

```
ForStRsIncrementalKeyedStateHandle
  extends AbstractIncrementalKeyedStateHandle

  字段:
  - metadataBlob: StreamStateHandle     // ForSt-RS 序列化的 VersionSet blob
  - sstFiles: Map<String, StreamStateHandle>  // SST 文件（shared scope）
  - metaStateHandle: StreamStateHandle  // Flink State meta info

  与 IncrementalRemoteKeyedStateHandle 的差异:
  - 无 miscFiles（没有 MANIFEST/CURRENT）
  - 新增 metadataBlob 字段
  - sstFiles 语义相同（增量 diff 追踪兼容）
```

### 3.2 快照策略

```
ForStRsIncrementalSnapshotStrategy
  extends SnapshotStrategy<KeyedStateHandle>

  syncPrepareResources():
    1. 通过 C ABI 调用 forst_rs_prepare_checkpoint()
    2. 获取 metadata_blob 和 live_sst_files
    3. 构建 PreviousSnapshot（复用现有逻辑）

  asyncSnapshot():
    1. 增量 diff：对比 live_sst_files 和 PreviousSnapshot
    2. 上传新增 SST 文件
    3. 上传 metadata_blob
    4. 构建 ForStRsIncrementalKeyedStateHandle
    5. enable_file_deletions()

  notifyCheckpointComplete():
    复用 ForStIncrementalSnapshotStrategy 的逻辑
    更新 uploadedSstFiles，清理过期记录
```

### 3.3 恢复操作

```
ForStRsRestoreOperation
  implements ForStRestoreOperation

  restore():
    1. 选择最佳 handle（findTheBestStateHandleForInitial）
    2. 下载文件到本地（ForStStateDataTransfer）
    3. 通过 C ABI 调用 forst_rs_restore()
    4. 如需 Rescaling → forst_rs_clip_key_group_range()
    5. 如需合并多 handle → forst_rs_ingest_external_files()
    6. 返回 ForStRsRestoreResult
```

## 5. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| metadata_blob 过大（包含冻结 MemTable） | 上传延迟增加 | LZ4 压缩 + 阈值控制（超过 128MB 则等待 flush） |
| Rescaling 后 Compaction 风暴 | 短期性能下降 | 限制恢复后首次 Compaction 的 IO 速率 |
| 并发 Checkpoint + Compaction 的 VersionSet 竞争 | 数据不一致 | ArcSwap 无锁原子替换 + Arc 引用计数 |
| 冻结 MemTable 恢复的内存峰值 | OOM 风险 | 恢复时先 flush 冻结 MemTable 到 SST，再正常运行 |
| 增量 diff 追踪与 ForSt 的兼容性 | 混合部署问题 | Java 侧 PreviousSnapshot 逻辑完全复用，仅 StateHandle 类型不同 |
