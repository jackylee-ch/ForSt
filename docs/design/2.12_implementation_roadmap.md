## 1. 路线图总览

### 1.1 三阶段战略

ForSt-RS 的实施采用**渐进式三阶段演进**战略。Phase 1 构建完整的状态存储引擎作为 ForSt/RocksDB 的直接替代（Drop-in Replacement），保持全部现有接口不变；Phase 2 重构 Java 侧接口释放 Arrow 零拷贝性能并引入单表 DeltaJoin；Phase 3 扩展到 Multi DeltaJoin、Remote Merge Service 与 Server-side Compaction。

```
Phase 1: 状态存储引擎 (短期, ~16 周)
  ├── P1.1 基础层 (forst-rs-common + forst-rs-io + S3)     ─── 4 周
  ├── P1.2 存储层 (SST + MemTable + Cache + VersionSet)     ─── 6 周
  └── P1.3 引擎层 (Engine + Compaction + Checkpoint + C ABI) ─── 6 周
  里程碑: ForSt-RS 可替代 ForSt 作为 Flink StateBackend，Java 侧零改动

Phase 2: 接口重构与 DeltaJoin (中期, ~12 周)
  ├── P2.1 Java Bridge 重构 (FFM + Arrow C Data Interface)   ─── 4 周
  ├── P2.2 Flink StateBackend 优化 (Arrow-native 状态访问)   ─── 4 周
  └── P2.3 DeltaJoin 本地化 (本地 prefix_scan Lookup)       ─── 4 周
  里程碑: Arrow 零拷贝状态访问 + DeltaJoin 本地 Lookup 可用

Phase 3: Multi DeltaJoin 与远端服务 (长期, ~12 周)
  ├── P3.1 Multi DeltaJoin (多维表合并为单实例查询)          ─── 4 周
  ├── P3.2 Remote Merge Service (SST 远端合并)               ─── 4 周
  └── P3.3 Server-side Compaction + 优化 (TM 资源卸载)      ─── 4 周
  里程碑: Multi DeltaJoin 可用，Server-side Compaction 降低 TM 资源占用

                                                          总计 ~40 周
```

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **自底向上** | 每个阶段交付一组可独立编译和测试的 crate/模块 |
| **零侵入优先** | Phase 1 不修改任何 Flink/Rust 现有接口，确保无缝 Drop-in 替换 |
| **渐进增强** | Phase 2 在引擎功能已验证的基础上重构接口释放 Arrow 零拷贝性能 |
| **延迟扩展** | Phase 3 的远端服务和多表能力建立在 Phase 1-2 的坚实基础上 |
| **自主生命周期** | ForSt-RS 完全自主管理数据摄入、存储、Compaction 和查询，不依赖任何外部系统 |
| **每 PR 审查** | 每个 PR 立即触发 10-Agent 并行审查循环，质量收敛后才推进下一任务 (Section 9) |
| **自主开发** | Phase 内部自主决策，不询问实现细节；基于 Flink PMC + 状态存储深厚经验判断 (Section 10) |

## 4. Phase 3: Multi DeltaJoin 与远端服务（长期，~12 周）

### 4.0 Phase 3 目标

扩展 DeltaJoin 到多维表联合查询（Multi DeltaJoin），引入 Remote Merge Service 合并多表 SST，并将 Compaction 卸载到远端服务以降低 TaskManager 资源占用。

### 4.1 P3.1: Multi DeltaJoin（4 周）

**目标**：支持 `A join B join C` 多维表场景。多张维表各自独立写入 ForSt-RS 实例，通过 SST 合并为统一视图，单次 prefix_scan 返回多表联合结果。

| 周 | 任务 | 模块 | 依赖 | 交付物 |
|----|------|------|------|--------|
| W29 | 多维表数据摄入 | flink/deltajoin | P2.3 | 每张维表独立 ForSt-RS 实例，独立 Flush → SST on S3 |
| W29 | SST 元数据注册 | engine/multi | engine | SST 输出事件通知机制，元数据收集 |
| W30 | ForStRsMultiJoinMergeCoordinator | flink/deltajoin | W29 | 协调多维表 SST 合并流程 |
| W30 | Key 前缀对齐 | engine/multi | engine | 统一 join_key 编码规范，多表 SST 按前缀对齐 |
| W31 | Merged View 读取 | engine/multi | W30 | 本地 ForSt-RS 读取 unified SST set |
| W31 | 单次 prefix_scan 多表结果 | engine/multi | W31 | 一次 prefix_scan 返回 A + B + C 联合结果 |
| W32 | Multi DeltaJoin 集成测试 | flink/deltajoin | all | A join B join C 端到端验证 |
| W32 | M9 验证 | all | all | Multi DeltaJoin 端到端 |

**M9 验收标准**：
- [ ] 3 张维表各自独立写入 ForSt-RS，SST 落入 S3
- [ ] Key 前缀对齐: 多表 SST 按相同 join_key 前缀组织
- [ ] Merged View: 单次 prefix_scan 返回 3 张维表的联合结果
- [ ] 性能: Multi DeltaJoin 3 表 Lookup < 传统 3 次独立 Lookup 延迟
- [ ] Checkpoint: Multi DeltaJoin failover 后数据一致
- [ ] 正确性: 与传统多次 Lookup 结果完全一致

### 4.2 P3.2: Remote Merge Service（4 周）

**目标**：构建独立的远程服务，负责将多张维表的 SST 文件按 join_key 前缀合并为统一 SST 集合。

| 周 | 任务 | 模块 | 依赖 | 交付物 |
|----|------|------|------|--------|
| W33 | Merge Service 核心骨架 | remote-service | engine | 独立服务进程，S3 读写能力 |
| W33 | 合并请求协议 | remote-service/proto | common | MergeRequest/MergeResponse 定义 |
| W34 | SST 合并引擎 | remote-service/merge | engine | 多表 SST 按 join_key 归并排序 → 统一 SST 输出 |
| W34 | 增量合并策略 | remote-service/merge | W34 | 仅处理增量变更 SST，避免全量重建 |
| W35 | 版本管理 | remote-service | W34 | 合并元数据（版本号、SST 映射关系）维护 |
| W35 | 客户端集成 | flink/deltajoin | W33 | RemoteMergeServiceClient 与 Flink TM 对接 |
| W36 | Remote Merge 端到端测试 | all | all | TM → Merge Service → unified SST → prefix_scan |
| W36 | 容错与降级 | remote-service | all | Merge Service 不可用时降级回多次 Lookup 模式 |

**P3.2 验收标准**：
- [ ] Merge Service: 接收 MergeRequest → S3 读取多表 SST → 合并 → 输出 unified SST
- [ ] 增量合并: 仅处理新增 SST，合并延迟 < 30s（典型场景）
- [ ] 容错: Merge Service 宕机后 TM 自动降级回多次 Lookup
- [ ] 性能: 合并后 prefix_scan 延迟 < 多次独立 prefix_scan
- [ ] 一致性: 合并结果与多次独立 Lookup 结果完全一致

### 4.3 P3.3: Server-side Compaction + 优化（4 周）

**目标**：将 Compaction 工作负载从 Flink TaskManager 卸载到远端服务，降低 TM CPU 和 I/O 压力。同时进行全面的性能优化和稳定性测试，达到生产就绪。

| 周 | 任务 | 模块 | 依赖 | 交付物 |
|----|------|------|------|--------|
| W37 | Remote Compaction Service | remote-service/compaction | P3.2 基础设施 | 复用 Merge Service S3 读写能力 |

| W40 | 压力测试 + M10 验证 | all | all | 7 天稳定性测试，生产就绪审查 |

**M10 验收标准**：
- [ ] Server-side Compaction: TM Compaction 请求 → 远端服务执行 → 结果正确
- [ ] TM 精简模式: Compaction 卸载后 TM CPU 峰值显著降低
- [ ] 回退机制: 远端服务不可用时自动回退到本地 Compaction
- [ ] 吞吐性能 >= ForSt 的 100%（Arrow 批量路径优势）
- [ ] P99 延迟 <= ForSt 的 P99 延迟（消除 JNI 开销）
- [ ] 7 天压力测试: 无内存泄漏（RSS 增长 < 5%）
- [ ] 7 天压力测试: 无 panic、无 data corruption
- [ ] BlockCache 命中率: >= ForSt 同条件下的命中率
- [ ] Compaction 写放大: <= ForSt Leveled Compaction 的 60%

### 4.4 Phase 3 里程碑总结

**Phase 3 交付物**：Multi DeltaJoin + Remote Merge Service + Server-side Compaction，生产就绪。

**核心收益**：
- Multi DeltaJoin: 单次 prefix_scan 返回多维表联合结果，延迟降低 N 倍
- Remote Merge Service: SST 级别合并，统一 BlockCache，提高数据局部性
- Server-side Compaction: TM 资源释放，CPU 峰值降低，专注数据摄入和查询
- 生产就绪: 全面性能优化 + 7 天稳定性验证

此决策门需要在 Phase 1 开始前完成。审批内容：

5. **资源需求**：需要多少 Rust 开发者和 Flink 开发者

### D-02-04: 三阶段演进策略（已决定）

| 选项 | 描述 | 结论 |
|------|------|------|
| 一步到位 | 直接实现完整 DeltaJoin + Remote Service | 不选：风险过高，交付周期过长，无法尽早获得反馈 |
| 两阶段 | Drop-in + 完整 DeltaJoin | 不选：缺少接口重构的过渡期，Single/Multi DeltaJoin 耦合 |
| **三阶段演进** | Drop-in → 接口重构 + Single DeltaJoin → Multi DeltaJoin + Remote Service | 选定：渐进式交付，每阶段有独立价值，风险可控 |

**决策依据**：
- **短期价值**：Drop-in 替换让现有用户零成本迁移，快速验证 ForSt-RS 引擎可靠性
- **中期价值**：Arrow-native 接口释放零拷贝性能红利；Single DeltaJoin 验证本地 Lookup 架构
- **长期价值**：Remote Merge Service 解锁多表联合查询；Server-side Compaction 降低 TM 负载
- **风险隔离**：每阶段独立可用，即使后续阶段推迟也不影响已交付功能

### 8.1 Phase 1 Benchmark：纯存储引擎验证

**目标**：验证 ForSt-RS 作为 Drop-in 替换，纯存储层性能 >= ForSt/RocksDB。

**执行时间**：W15-W16（M5 验证阶段）

#### BM-1.1: 点查性能 (Point Lookup)

| 参数 | 配置 |
|------|------|
| 操作 | `get(key)` 单条点查 |
| Key 分布 | uniform + Zipf(0.99) + Zipf(1.5) |
| 数据规模 | 1GB / 10GB / 100GB state |
| BlockCache | 256MB / 1GB / 4GB |
| 线程数 | 1 / 4 / 16 |
| 度量 | P50/P99/P999 延迟, ops/sec, CPU%, cache hit rate |

**预期结论**：
- Cache hit 场景：ForSt-RS 1.5-3x 优于 ForSt（ShardedClock 无锁 vs LRU 锁竞争）
- Cache miss 场景：ForSt-RS ~1.0x（受限于 S3/磁盘 IO，与 ForSt 相当）
- **可解释性**：Lock-free CAS 消除多线程场景的 mutex 争用；Arrow DataBlock 64KB 减少随机 IO 次数

#### BM-1.2: 批量读写性能 (Batch Operations)

| 参数 | 配置 |
|------|------|
| 操作 | `batch_get(100 keys)` / `batch_put(100 entries)` |
| Batch 大小 | 1 / 10 / 100 / 1000 |
| 数据规模 | 10GB state |
| 度量 | 吞吐 (batches/sec), 单 batch 延迟, 每条均摊延迟 |

**预期结论**：
- batch_get 100 keys：ForSt-RS 3-4x（共享 Block 加载 + 批量 Bloom 查询 + 单次 C ABI 调用 vs 100 次 JNI）
- batch_put 100 entries：ForSt-RS 3-5x（单次 RecordBatch 写入 vs 100 次 JNI + 100 次 memcpy）
- **可解释性**：批量操作摊销了 C ABI 调用开销和 RecordBatch 构造成本

#### BM-1.3: 写入吞吐 (Write Throughput)

| 参数 | 配置 |
|------|------|
| 操作 | 持续 `batch_write` 直到触发 Compaction |
| 写入速率 | 不限（最大吞吐） |
| MemTable 大小 | 64MB / 256MB |
| 度量 | 写入吞吐 (MB/s), Flush 延迟, Compaction 写放大, L0 stall 频率 |

**预期结论**：
- 写入吞吐：ForSt-RS 2-4x（Arena 分配 + Arrow 批量写入 vs SkipList 逐条插入）
- 写放大：ForSt-RS 12-15x（Tiered-Leveled 混合 vs ForSt Leveled 30-60x）
- **可解释性**：SortedRunArray 追加写入 + 64B 对齐 Arena 消除逐行分配开销

#### BM-1.4: Checkpoint/Restore 性能

| 参数 | 配置 |
|------|------|
| 操作 | Checkpoint (sync + async) → Restore |
| State 规模 | 1GB / 10GB / 100GB |
| MemTable 大小 | 64MB / 256MB |
| 度量 | 同步阶段耗时, Blob 大小, Restore 耗时, 端到端耗时 |

**预期结论**：
- 同步阶段：ForSt-RS <1ms（ArcSwap 原子切换 vs ForSt MemTable 刷盘等待）
- Restore：ForSt-RS <10ms（blob 反序列化 vs ForSt MANIFEST 回放）
- **可解释性**：Mode B 消除 MANIFEST 持久化和回放开销；VersionSet 内存驻留

#### BM-1.5: Compaction 效率

| 参数 | 配置 |
|------|------|
| 操作 | 持续写入触发 L0→L1→L2 Compaction |
| 数据规模 | 写入 50GB 数据 |
| 度量 | 写放大, Compaction 吞吐 (MB/s), 读放大, 空间放大 |

**预期结论**：
- 写放大 12-15x（Tiered L0-L2 + Leveled L3+）
- Compaction 吞吐 >= ForSt（Arrow 列式归并排序 + SIMD key 比较）

**Phase 1 Go/No-Go 标准**：
| 指标 | 门槛 | 说明 |
|------|------|------|
| 点查 P50 (cache hit) | <= ForSt * 1.2x | 允许 20% 内的回归（Phase 2 FFM 优化会补回） |
| 批量操作吞吐 | >= ForSt * 1.5x | 必须显示 Arrow 批量优势 |
| 写入吞吐 | >= ForSt * 1.0x | 至少不低于 ForSt |
| Checkpoint 同步阶段 | <= 1ms | Mode B 核心优势必须体现 |
| 7 天稳定性 | 零 panic, RSS 增长 <5% | 基本可靠性 |

### 8.2 Phase 2 Benchmark：Flink 端到端验证

**目标**：验证 FFM Bridge + Arrow-native StateBackend 在真实 Flink 作业中的端到端性能收益，以及 DeltaJoin 本地 Lookup 延迟。

**执行时间**：W24（M7 验证）+ W28（M8 验证）

#### BM-2.1: Nexmark Streaming Benchmark

使用 Nexmark 标准流式 Benchmark 覆盖不同算子类型：

| 查询 | 算子类型 | 状态类型 | 目的 |
|------|---------|---------|------|
| Q2 (Selection) | Filter + Map | 无状态 | 基线——无状态作业的框架开销对比 |
| Q5 (Hot Items) | Window Aggregate | ValueState | Window + Timer 密集型 |
| Q7 (Highest Bid) | Session Window + Join | MapState + ListState | 复杂状态访问模式 |
| Q8 (Monitor New Users) | Tumbling Window + Join | ValueState + MapState | 双流 Join |
| Q11 (User Sessions) | Session Window | ListState | Session 语义 + Timer |

每个查询运行 **30 分钟**，采集：
- 吞吐 (events/sec)
- P50/P99/P999 端到端延迟
- Checkpoint 耗时 (sync + async)
- CPU / Memory / GC 指标
- 状态大小增长曲线

**预期结论**：
- 无状态查询 (Q2)：~1.0x（无状态访问，收益来自框架开销差异）
- 聚合查询 (Q5)：1.5-2.5x 吞吐提升（batch state access + 零拷贝）
- 复杂 Join (Q7/Q8)：1.3-2.0x（State IO 占比高，受 TypeSerializer 限制）
- Session Window (Q11)：1.2-1.8x（Timer 密集，Timer 层未优化）
- **可解释性**：按 Amdahl 分解——State IO 改善 * State IO 占总耗时比例 = 端到端改善

#### BM-2.2: 状态访问微基准 (State Micro-benchmark)

隔离测试 5 种 Flink 状态类型的读写性能：

| 状态类型 | 操作 | Batch 大小 | 度量 |
|---------|------|-----------|------|
| ValueState | get + update | 1 / 10 / 100 | ops/sec, P50/P99 |
| ListState | add + get + clear | 1 / 10 / 100 | ops/sec, P50/P99 |
| MapState | put + get + keys + entries | 1 / 10 / 100 | ops/sec, P50/P99 |
| ReducingState | add + get | 1 / 10 / 100 | ops/sec, P50/P99 |
| AggregatingState | add + get | 1 / 10 / 100 | ops/sec, P50/P99 |

每种状态类型测试 3 种 state 规模：1GB / 10GB / 100GB。

**预期结论**：
- Batch=1：1.3-1.8x（消除 JNI 开销，但单条操作收益有限）
- Batch=100：2.5-4x（Arrow 批量路径摊销 FFM 调用和 RecordBatch 构造成本）
- **可解释性**：Batch=1 时 TypeSerializer 编解码占 30-40% 不可优化；Batch=100 时 FFM+Arrow 的固定开销被摊销

#### BM-2.3: DeltaJoin Lookup 延迟

| 场景 | 配置 | 度量 |
|------|------|------|
| 热数据 Lookup | 维表 1GB, Cache 4GB, 100% cache hit | P50/P99 延迟, QPS |
| 温数据 Lookup | 维表 10GB, Cache 1GB, ~80% cache hit | P50/P99 延迟, QPS |
| 冷数据 Lookup | 维表 100GB, Cache 256MB, ~30% cache hit | P50/P99 延迟, QPS |
| 恢复速度 | 维表 10GB, 从 Checkpoint 恢复 | 恢复耗时, 首次 Lookup 延迟 |
| Rescaling | 维表 10GB, 并行度 4→8 | 扩容耗时, 扩容后 P99 延迟 |

**预期结论**：
- 热数据 P50 < 10us（本地 BlockCache hit，零 RPC）
- 温数据 P50 < 100us（SSD Cache hit）
- 冷数据 P50 1-50ms（S3 fetch，与远程 RPC 相当但无网络额外开销）
- 恢复速度 < 10ms（blob 反序列化，本地无状态）
- **可解释性**：消除网络往返是热/温数据延迟改善的核心因素；冷数据受限于 S3 延迟

**Phase 2 Go/No-Go 标准**：
| 指标 | 门槛 | 说明 |
|------|------|------|
| Nexmark Q5 吞吐 | >= ForSt * 1.3x | 聚合场景必须有明确收益 |
| Nexmark Q7 吞吐 | >= ForSt * 1.2x | Join 场景至少有可见收益 |
| DeltaJoin 热数据 P50 | < 100us | 本地 Lookup 核心价值 |
| DeltaJoin 恢复速度 | < 1s（含 Cache 预热） | 无状态快速恢复 |
| Checkpoint 端到端 | <= ForSt * 0.8x | Checkpoint 耗时降低 20%+ |

### 8.3 Phase 3 Benchmark：Multi DeltaJoin 与远端服务验证

**目标**：验证 Multi DeltaJoin 单次 prefix_scan 的多表联合查询收益，以及 Server-side Compaction 的 TM 资源卸载效果。

**执行时间**：W32（M9 验证）+ W40（M10 验证）

#### BM-3.1: Multi DeltaJoin 延迟对比

| 场景 | 传统方案（对照） | Multi DeltaJoin | 度量 |
|------|----------------|-----------------|------|
| 2 维表 Join | 2 次独立 prefix_scan | 1 次 prefix_scan | P50/P99 延迟, QPS |
| 3 维表 Join | 3 次独立 prefix_scan | 1 次 prefix_scan | P50/P99 延迟, QPS |
| 5 维表 Join | 5 次独立 prefix_scan | 1 次 prefix_scan | P50/P99 延迟, QPS |

每个场景测试热数据（cache hit >90%）和温数据（cache hit ~60%）两档。

**预期结论**：
- 热数据 3 表 Join：P50 从 <30us（3x10us）降至 <15us（数据物理相邻）

#### BM-3.2: Remote Merge Service 效率

| 合并延迟 | 从 SST 输出到 Merged View 可用的时间 |

**预期结论**：
- 增量合并延迟 < 30s（典型场景，3 张维表各 10GB）
- 增量合并 IO << 全量重建 IO（仅处理变更 SST）

#### BM-3.3: Server-side Compaction 资源卸载

| 指标 | TM 内 Compaction（对照） | Server-side Compaction | 改善 |
|------|------------------------|----------------------|------|
| TM CPU 峰值 | 测量 | 测量 | 期望降低 40-60% |
| TM 内存 RSS | 测量 | 测量 | 期望降低 10-20% |
| Compaction 吞吐 | 测量 | 测量 | 期望 >= 1.0x |
| 写放大 | 测量 | 测量 | 期望不变 |
| 读延迟 P99 | 测量 | 测量 | 期望改善（Compaction 不抢 TM IO） |

**预期结论**：
- TM CPU 峰值降低 40-60%（Compaction IO 密集操作移出 TM）
- **可解释性**：SST 已在 S3，Compaction 服务直接读写 S3，TM 无额外网络传输

## 9. PR Review 自动化审查流程

> **原则**：每完成 1 个 PR（即 1 个逻辑完整的 commit 组），立即执行多 Agent 并行审查，**不等到 Phase 结束**。审查-修复循环持续进行，直到代码质量收敛。

### 9.1 审查触发时机

```
开发流程:
  编码 → commit → PR Review 循环 → 质量收敛 → 推进下一任务
       ↑                                          |
       └──────────────────────────────────────────┘

NOT:
  编码 → commit → 编码 → commit → ... → Phase 结束 → 集中 Review（过晚！）
```

**触发条件**：每当一个逻辑 PR 完成（即 `git commit` 包含一个完整的功能单元、bug fix 或重构），**立即**启动 PR Review 循环。PR 粒度参考：
- 1 个新模块/crate 的初始实现
- 1 个 trait + 实现 + 单元测试
- 1 个 Bug fix（含回归测试）
- 1 个 Benchmark 脚本 + 结果报告

### 9.2 10-Agent 并行审查机制

每轮审查启动 **10 个独立子 Agent**，分别从不同维度审查最新 commit 的 diff：

| Agent # | 审查维度 | 检查重点 |
|---------|---------|---------|
| Agent 1 | **正确性 (Correctness)** | 逻辑错误、边界条件、off-by-one、空指针、溢出 |
| Agent 2 | **内存安全 (Memory Safety)** | Rust: lifetime/borrow 问题; Java: 内存泄漏、资源未关闭; Arrow 内存生命周期 |
| Agent 3 | **并发安全 (Concurrency)** | 数据竞争、死锁、锁顺序、原子操作正确性、Send/Sync trait 约束 |
| Agent 4 | **性能 (Performance)** | 不必要的拷贝、分配热点、O(n²) 算法、缓存不友好的访问模式、SIMD 可优化点 |
| Agent 5 | **API 设计 (API Design)** | 接口一致性、命名规范、向后兼容性、文档完整性、pub 可见性最小化 |
| Agent 6 | **错误处理 (Error Handling)** | 未处理的 Result/Option、error 上下文丢失、panic 路径、错误传播链完整性 |
| Agent 7 | **测试充分性 (Test Coverage)** | 遗漏的边界测试、缺失的负面测试、mock 正确性、测试隔离性、覆盖率评估 |
| Agent 8 | **架构一致性 (Architecture)** | 是否符合 5 层架构、模块边界清晰、依赖方向正确（下层不依赖上层）、与设计文档一致 |
| Agent 9 | **安全性 (Security)** | unsafe 代码审查、输入校验、整数溢出、路径遍历、信息泄漏 |
| Agent 10 | **代码风格与规范 (Style)** | Rust clippy/fmt 合规、Java Checkstyle 合规、命名规范、注释质量、文件组织 |

### 9.3 问题分级标准

| 级别 | 定义 | 示例 | 处置 |
|------|------|------|------|
| **High** | 影响正确性、安全性或会导致生产事故的问题 | 数据竞争、内存泄漏、逻辑错误导致数据丢失、panic 未捕获 | **必须修复** |
| **Medium** | 影响性能、可维护性或违反架构约定的问题 | 不必要的 clone、pub 过宽、缺少关键测试、错误信息不清晰 | **必须修复** |
| **Low** | 风格建议、微优化、非关键文档缺失 | 变量命名偏好、注释格式、可选的 SIMD 优化 | **记录但不阻塞** |

### 9.4 审查-修复循环流程

```
Round N:
  ┌─────────────────────────────────────────────────┐
  │ 1. 启动 10 个子 Agent 并行审查最新 commit diff  │
  │ 2. 各 Agent 独立产出问题列表 (High/Medium/Low)  │
  │ 3. 汇总去重 → 生成 Round N 审查报告            │
  │ 4. 统计: High 数量, Medium 数量, Low 数量       │
  ├─────────────────────────────────────────────────┤
  │ 5. 若 High > 0 或 Medium > 0:                   │
  │    a. 逐一修复 High issues                      │
  │    b. 逐一修复 Medium issues                    │
  │    c. 编译验证: cargo build / mvn compile        │
  │    d. 逻辑验证: cargo test / mvn test            │
  │    e. 提交修复: git commit -m "fix: ..."         │
  │    f. → 进入 Round N+1                          │
  ├─────────────────────────────────────────────────┤
  │ 6. 若 High == 0 且 Medium == 0:                  │
  │    clean_rounds += 1                             │
  │    → 进入 Round N+1 (继续验证收敛)              │
  └─────────────────────────────────────────────────┘

终止条件 (满足任一即停止):
  ✓ 连续 10 轮 High == 0 且 Medium == 0  → 质量收敛，PR 通过
  ✗ 累计达到 100 轮                       → 强制停止，人工介入
```

### 9.6 与 Phase Benchmark 的关系

```
Phase 内部:
  Task 1 → PR → Review 循环 → 收敛 ✓
  Task 2 → PR → Review 循环 → 收敛 ✓
  Task 3 → PR → Review 循环 → 收敛 ✓
  ...
  最后一个 Task → PR → Review 循环 → 收敛 ✓
  → Phase Benchmark (Section 8) → Go/No-Go 判定 → 进入下一 Phase
```

PR Review 关注**代码质量**（正确性、安全性、性能、架构），Phase Benchmark 关注**系统级性能指标**（吞吐、延迟、稳定性）。两者互补，不替代。

### 9.7 特殊场景处理

| 场景 | 处理方式 |
|------|---------|
| 100 轮未收敛 | 强制停止，生成诊断报告，标注反复出现的问题模式，请求人工决策 |
| Agent 之间结论矛盾 | 以更高级别为准（如 Agent 4 说 Low、Agent 3 说 High → 按 High 处理） |
| 修复引入新问题 | 下一轮 Agent 会捕获新问题，循环继续（这就是多轮审查的价值） |
| 跨 PR 依赖的架构问题 | Agent 8 (架构一致性) 在每个 PR 都检查，累积偏差会在早期被发现 |
| 纯文档 / 配置变更 PR | 仍执行审查（Agent 5 API + Agent 10 Style），但预期 1-2 轮收敛 |

## 10. 自主开发模式与决策原则

> **原则**：一旦进入开发阶段，除非到达 Phase 边界（Phase 1→2、Phase 2→3），否则不主动询问实现细节或给出方案选择。基于 Flink 社区 10 年 PMC 经验和状态存储领域的深厚积累，自主完成全部重构和升级决策。

### 10.1 自主决策边界

| 决策类型 | 自主执行 | 需要确认 |
|---------|---------|---------|
| **实现细节**：数据结构选择、算法优化、内存布局 | 自主判断 | — |
| **错误处理策略**：Result vs panic vs fallback 选择 | 自主判断 | — |
| **性能权衡**：空间换时间、预计算 vs 惰性计算 | 自主判断 | — |
| **测试策略**：测试粒度、mock 范围、集成测试边界 | 自主判断 | — |
| **重构决策**：提取 trait、拆分模块、消除重复 | 自主判断 | — |
| **依赖选择**：crate 版本、feature flag 组合 | 自主判断 | — |
| **Phase 内里程碑调整**：任务拆分或合并 | 自主判断 | — |
| **Phase 边界决策**：是否满足进入下一 Phase 的条件 | — | 需确认 |

### 10.2 决策依据体系

自主决策时参考以下优先级排序的知识来源：

   - ColumnFamily 隔离设计

### 10.3 Phase 内开发节奏

```
Phase N 开始:
  ├── 读取该 Phase 的设计文档和任务列表
  ├── 按路线图顺序逐个 Task 执行:
  │     Task K:
  │       1. 编码实现（TDD: 先测试 → 后实现 → 重构）
  │       2. git commit
  │       3. PR Review 循环 (Section 9)
  │       4. 质量收敛 → 推进到 Task K+1
  │
  ├── Phase 最后一个 Task 完成后:
  │     5. Benchmark 验证 (Section 8)
  │     6. Go/No-Go 判定
  │
  └── Phase N 结束 → **暂停，等待用户确认进入 Phase N+1**
```

**Phase 内不暂停的场景**：
- 遇到技术实现困难（自主寻找替代方案）
- 需要调整 Task 顺序或粒度（自主重排）
- 发现设计文档有小矛盾（以更具体的描述为准，记录偏差）
- 需要添加设计文档未预见的辅助工具/测试基础设施（自主添加）

**Phase 内暂停的场景**：
- 发现设计文档有**根本性错误**（如架构方向冲突）
- Benchmark 结果严重低于预期（Go/No-Go 判定失败）
- 100 轮 PR Review 未收敛（Section 9.7）

### 10.4 典型自主决策示例

以下为开发过程中可能遇到的典型决策及其自主判断依据：

| 场景 | 决策 | 依据 |
|------|------|------|
| MemTable 排序实现选择 | SortedRunArray (batch 追加 + 后台排序) | 写入密集型场景 batch 吞吐优先；参考 ForSt UDT CompactionMergeIterator 演化 |
| BlockCache 淘汰算法 | ShardedClock (16 分片无锁) | 多线程场景 Lock-free 优于 LRU + Mutex；参考 LIRS/CLOCK-Pro 论文 + RocksDB Clock Cache |
| Compaction 文件选择 | Tiered L0-L2 + Leveled L3+ | 平衡写放大与读放大；参考 RocksDB Universal Compaction 经验 + Dostoevsky 论文 |
| Arrow RecordBatch 大小 | 64KB 默认，可配置 32KB-256KB | 参考 Arrow IPC 推荐 + 实测 L1/L2 Cache Line 对齐 |
| FFM vs JNI 切换逻辑 | Runtime 检测 JDK 版本，FFM-first | 参考 Flink ForStStateBackend 的 JNI 模式切换经验 |
| Error 类型粒度 | 细粒度枚举 (IoError/CorruptionError/...) | 参考 RocksDB Status 设计 + Rust thiserror 惯用模式 |
| 测试 mock 策略 | MemoryFs 替代真实 IO；MockClock 替代系统时间 | 参考 RocksDB Env 抽象层测试模式 |
| Checkpoint 序列化格式 | 自定义二进制 (version + length-prefixed fields) | 紧凑 + 快速反序列化；参考 Flink Checkpoint Metadata 格式 |
